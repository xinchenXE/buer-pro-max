# buer-pro-max

> 把一套**跨会话的项目治理体系**装进任意仓库的**通用 Agent Skill**。
>
> 它解决的不是「怎么写文档」，而是**「下一个会话凭什么知道这一轮发生了什么、下一步该做什么」**。
>
> **不绑定任何宿主**：内容是**纯 Markdown + 一个自检脚本（Python 3，仅维护期需要）**，
> 没有任何宿主 API、SDK 或工具调用依赖。Claude Code / Codex / Cursor / Gemini CLI /
> 其他读 `AGENTS.md` 约定或支持 skill / 规则目录的 agent 都能用 ——
> **只有「装到哪个目录」这一步由宿主决定**（见 §一）。
>
> **独立产物**：不包含任何具体项目的内容，独立迭代，与任何项目的更新节奏无关。
> 其中的规则形态与教训来自长期的真实开发实践 —— **主要出自
> `deepseek-harness-desktop-master`（`dsh GalGame`）的治理实践**（70+ 轮），
> 踩出来的坑都在 `references/anti-patterns.md` 里。
>
> **溯源 ≠ 归属**：标明经验从哪来，是为了让每条教训可考、可追；
> 但 skill 本身**不归那个项目管理**，也不随它演进。

> **升级已安装的副本**：见 **§一·补 拉取更新** —— clone 安装的只需一条 `git pull --ff-only`。

## 〇、适用场景：什么时候该用它，什么时候别用

> **一句话判据**：**「下一个会话要花多久才能知道你上一次干到哪？」**
> 有现成答案（issue tracker + 每轮都写 PR 描述）→ **别装**。没有 → 装。

### ✅ 适合

| 场景 | 为什么它有用 |
|---|---|
| **单人维护、但跨很多会话的中大型项目** | 每开一个新会话都要重新发现上下文 → 这是它要解决的第一问题。典型信号：5k 行以上、跨 3 个以上会话仍在改同一个系统 |
| **被 AI 反复「失忆」的项目** | 同一个问题被改了两次、上一轮的结论被推翻又重做、计划写完没人按计划走 |
| **有只读边界的项目** | 有上游 / 生成物 / 第三方封装 / 冻结配置 —— 铁律 ①② 与可写范围表本来就是为这类边界设计的 |
| **需要对「谁批准了什么」留下证据的项目** | 单人时靠章程与留痕；多人时升到重型档，有角色矩阵与不可变台账 |
| **已经有零散文档、想统一信息架构** | 分析文档、TODO、ROADMAP 散在根目录 → 给它一个索引与唯一的计数真源 |
| **已有治理体系、想审计它** | 走「审计模式」：只报告它违反了自己声明的哪些规则，**不按本 skill 的模板改造它** |

### ⛔ 不适合

| 场景 | 为什么别用 |
|---|---|
| **一次性的小脚本 / 周末实验**（1–2 个源文件、不打算回来维护） | 判出**微型档**时它会直接说「别装」，只给一份约 15 行的 `NEXT.md`。**装治理只有坏处**：你会填一份没人读的模板，而它的存在会让你以为自己有治理 |
| **5k 行以下的单人小工具** | 轻量档能用，但**先掂量成本**：判据是「每周花在治理上超过 10 分钟 → 它在拖累你」 |
| **已有成熟 issue tracker + CI + 每轮都写 PR 描述** | 本 skill 的队列 / 问题 / 偏差序列**与它们重复**。重复的记账会互相漂移，比只有一套更糟 |
| **多人协作、有正式发布列车的团队** | 它**能**升到重型档，但那种规模通常该用真正的项目管理工具，而不是一套 Markdown 治理树 |
| **需要强制流程的合规场景** | 它的约束是**纪律 + 门禁**，不是审批系统。**没有权限执行的东西，它不会假装有** |
| **你只想要一个「更长的 CLAUDE.md」** | 它的价值在**容器、序列与闭环仪式**；只想要一段规则说明，写 `AGENTS.md` 就够了 |

### 判断用的三个问题

1. **这个项目会活过 10 个会话吗？** 不会 → 别装。
2. **你上一次找「这轮到底改了啥」花了多久？** 超过 5 分钟 → 需要。
3. **有没有你绝对不许改的东西？** 有 → 可写范围表与硬停清单会立刻有用；没有 → 那些条目会退化成空话，生成时会写明「为什么没启用」。

> **它不便宜。** 完整档一次性要填十几份文档，每轮收尾要走 7 步 + 交接件。
> **它防的是返工，不是省事。** 如果你的项目返工不贵，装它大概率是净亏。

## 一、安装

它是一个**通用 Agent Skill**：一份目录，里面是纯 Markdown 规则 + 模板 + 一个自检脚本。
**没有构建步骤、没有运行时依赖、没有宿主 SDK**。装法只有一个动作 ——
**把整个目录放到宿主约定的 skills / 规则目录下**。

### 1. 选装在哪一级

| 级别 | 路径 | 谁能用 | 什么时候选 |
|---|---|---|---|
| **用户级** | `~/.claude/skills/buer-pro-max/` | 你这台机器上的**所有**项目 | 默认选它 —— 大多数人是「在几个项目之间都用同一套治理」 |
| **项目级** | `<项目根>/.claude/skills/buer-pro-max/` | 只有那个项目 | 想让它跟项目一起提交、或不同项目需要不同版本时 |

> **不要两边都装同一份**。宿主会看到两个同名 skill，加载哪个取决于它的查找顺序 ——
> 你会在一个项目里按旧版规则行事，且**没有任何报错**。

### 2. 安装（推荐 `git clone`）

**推荐 clone。** 装进去的文件是同一份，差别在装完之后：clone 装的升级是一条
`git pull`，还能看到版本历史、知道自己落后了多少个版本；下载 zip / 拷目录装的没有
版本历史，每次升级都要重新下载再整目录替换，而且**无法确认自己落后多少**。
升级命令见 **§一·补 拉取更新**。

```sh
# 用户级（macOS / Linux / git-bash）
git clone https://github.com/xinchenXE/buer-pro-max.git ~/.claude/skills/buer-pro-max

# 项目级
git clone https://github.com/xinchenXE/buer-pro-max.git <项目根>/.claude/skills/buer-pro-max
```

```powershell
# Windows PowerShell —— 用户级
git clone https://github.com/xinchenXE/buer-pro-max.git "$env:USERPROFILE\.claude\skills\buer-pro-max"

# Windows PowerShell —— 项目级
git clone https://github.com/xinchenXE/buer-pro-max.git "<项目根>\.claude\skills\buer-pro-max"
```

> **国内网络**：把 URL 换成镜像 `https://cnb.cool/xinchenXE/buer-pro-max.git`，
> 内容与 GitHub 完全一致（两个远端由维护者同步推送）。

**拷贝安装（不能 clone 时）**：把整个目录放到上表的位置即可。
代价是升级时只能**整目录替换** —— 先备份、删旧目录、再拷新的，**不要直接覆盖**；
覆盖会让「旧版有、新版删掉」的文件残留下来。步骤见 §一·补 第 4 条。

```sh
cp -r buer-pro-max ~/.claude/skills/
```

### 3. 其他宿主

| 宿主 | 放哪 | 备注 |
|---|---|---|
| **Codex** | `$CODEX_HOME/skills/`（默认 `~/.codex/skills/`） | 同上：clone 进去 |
| **Cursor** | 项目内 `.cursor/rules/`，或把 `SKILL.md` 作为规则文档喂给它 | Cursor 不读 skill 目录，读规则 |
| **Gemini CLI / 其他** | 该工具自己文档写的 skill / 规则位置 | **不要猜路径** —— 查它的文档 |
| **任何没有 skill 机制的 agent** | 直接把 `SKILL.md` 当规范贴进上下文，`references/` 放在可达位置 | 退化为「一份很长的规则文档」，仍然有效 |

### 4. 装完先确认再触发

```sh
cd ~/.claude/skills/buer-pro-max
rg '^\s*version:' SKILL.md          # 应看到 metadata.version
python scripts/selfcheck.py         # 可选（要有 Python 3）：必须 failed=0
```

- **目录名建议就叫 `buer-pro-max`** —— 与 frontmatter 里的 `name` 一致，避免两个名字在脑子里并存。
- `selfcheck.py` 只在**维护**这个 skill 时才需要；**使用**它零依赖。
  但装完跑一次能立刻排除「clone 下来的是个发布前提交」这种可能。

### 5. 触发

装好后在**新会话**里说 **「给这个项目建立治理」**、**「建立治理框架」**、
**「bootstrap governance」**、**「set up a dev paradigm」** 等即可触发
（完整触发词见 `SKILL.md` 的 `description`）。

> **新装的 skill 可能要开新会话才生效** —— 宿主在会话启动时加载技能描述，
> 已在跑的会话不会中途发现它。
>
> **如果你的宿主不支持「自动加载技能描述」**：直接把 `SKILL.md` 开头那段
> `description` 贴给 agent，或说「读 `SKILL.md` 并按它执行」。

### 6. 依赖

- **读取 / 使用本 skill：零依赖。** 它是纯 Markdown。
- **维护它自己**（改完跑自检）：需要 **Python 3**，只用标准库，无第三方包。
- **生成出来的产物**：也是纯 Markdown 与配置文本，**不依赖任何 agent**。

> **产物天然跨工具**：写进 `AGENTS.md` 的宪法段 + `<GOV_ROOT>/` 文档树都是纯文本。
> 任何读 `AGENTS.md` 约定的工具都能吃到同一份规则。
> 只有一件事是宿主相关的：**宪法段必须落到那个宿主真正会自动加载的文件里**
> —— 见 `templates/_宪法段模板.md` §五 的三选一。

## 一·补、拉取更新（升级已安装的副本）

> **先说清一件事：更新这个 skill ≠ 更新某个项目里的治理树。**
> 这两条线完全独立（见 §三「独立产物」）：
>
> - **本 skill** 是一棵**只读的规则与模板库**，更新它只是让**下一次**生成更准；
> - **已生成的 `<GOV_ROOT>/`** 是那个项目自己的资产，**不会**因为拉取 skill 而改变。
>   要让它跟上新版规则，走 **`references/audit-and-evolve.md` §三 版本对齐**（见本节第 6 条）；
>   要改变它的结构，走 `SKILL.md` §四 的**演进模式**。两者都不是 `git pull`。
>
> 所以：**拉取更新永远是安全的** —— 它不会动任何目标项目里的文件。

### 1. 两种安装方式，升级方式不同

| 你怎么装的 | 能否原地升级 | 怎么升级 |
|---|---|---|
| **`git clone` 到 skills 目录**（推荐） | ✅ | `git pull --ff-only` |
| **`cp -r` / 解压 zip 拷过去** | ❌ 副本没有版本历史 | 只能**整目录替换** —— 备份旧目录 → `git clone` 到原位置 → 删掉备份；见下面第 4 条 |

> **拷贝装的也能换成 clone 装**（推荐这么做）：先按第 4 条备份并删掉旧目录，
> 再 `git clone` 到同一路径。它不叫「拉取」，但换完就再也不用重新下载了。

### 2. clone 安装后的升级（一条命令）

```sh
# 用户级安装（~/.claude/skills/buer-pro-max）
git -C ~/.claude/skills/buer-pro-max pull --ff-only

# 项目级安装（<项目根>/.claude/skills/buer-pro-max）
git -C <项目根>/.claude/skills/buer-pro-max pull --ff-only
```

```powershell
# Windows PowerShell
git -C "$env:USERPROFILE\.claude\skills\buer-pro-max" pull --ff-only
```

**首次安装用 clone**：

```sh
git clone https://github.com/xinchenXE/buer-pro-max.git ~/.claude/skills/buer-pro-max
# 国内网络可用镜像（内容相同）
git clone https://cnb.cool/xinchenXE/buer-pro-max.git ~/.claude/skills/buer-pro-max
```

> **用 `--ff-only`，不要用 `git pull --rebase` 或 `merge`。**
> 这个目录是**被消费的库**，不是你的工作区。如果你在本地改过它（不推荐 ——
> 要改就 fork），`--ff-only` 会**失败并保留你的改动**，这正是想要的：
> 让你先看清冲突，而不是让 git 静默合并出一份混合版本。

### 3. 升级后确认（三步，别跳过）

```sh
cd ~/.claude/skills/buer-pro-max
rg '^\s*version:' SKILL.md          # 1. 当前版本
python scripts/selfcheck.py         # 2. 必须 failed=0
git log --oneline -5                # 3. 这次拉到了什么
```

- **第 2 步只在本地有 Python 3 时能做** —— 它检查的是 skill 自身的一致性，
  没有第三方依赖。跑出 `failed≠0` 说明你拉到的是一个**发布前**的提交：
  切回去（`git checkout <上一个 tag 或提交>`），并把自检输出贴给维护者。
- **宿主可能缓存技能描述** —— 版本变了却仍按旧触发词行为，**开一个新会话**即可。

### 4. 用拷贝方式安装的，怎么升级

没有版本历史，只能**整目录替换**。两条纪律：

1. **先备份**，再删旧目录、拷新目录 —— 不要「覆盖进去」（旧版有、新版删掉的文件
   会残留在原地，而这些残留文件正是自检 `orphan-files` 要抓的东西）。
2. **确认你从没在那里改过东西**。改过的部分会随旧目录一起消失。

```sh
mv ~/.claude/skills/buer-pro-max ~/.claude/skills/buer-pro-max.bak-$(date +%Y%m%d)
git clone https://github.com/xinchenXE/buer-pro-max.git ~/.claude/skills/buer-pro-max
```

### 5. 版本语义

- **版本号唯一权威在 `SKILL.md` 的 `metadata.version`**；§十 只记「为什么升版」。
- **版本按「不兼容 / 兼容」两条线递增**：
  - **新增或修正规则、措辞、模板（向后兼容）** → 递增**次版本**（`1.5.17` → `1.6.0` 之后为 `1.6.1`、`1.6.2`…）；
  - **不兼容变更**（改变已有产物的含义、需要目标项目做迁移步骤）→ 递增**主版本**
    （`1.x` → `2.0.0`），并在 §十 对应条目首行写 `⚠ 不兼容` 与迁移步骤。
  - 当前线：**1.6 系列**。1.5.x 的最后一个版本是 `1.5.17`。
- **更新频率与任何项目无关** —— 它是独立迭代的库，什么时候有改动什么时候推。
  想看「我落后了多久」：`git -C <skills 目录> log --oneline HEAD..origin/main`。

### 6. 更新 skill 之后，项目里的治理怎么办

**`git pull` 不会动你项目里已经生成的 `<GOV_ROOT>/`。** 要让那棵树跟上新版规则，
按 `references/audit-and-evolve.md` §三 的**版本对齐**流程走：

```
拉取并确认失败为 0 → 圈定作用域（模板必更 / 正文分在途与已闭环）
→ 差异审计（只报告不改）→ 逐条裁决 → 只改规则载体 → 留痕 → 判据全中
```

**核心区分：模板往后生效，历史原样保留。**

| ✅ 更新 | ❌ 不改 |
|---|---|
| **模板**（`_问题模板.md` / `_偏差模板.md` / `_记录模板.md` / `_队列项模板.md`、容器 README）—— **决定下一次登记长什么样** | **已登记的归档正文**：`归档计划/` `归档文档/` `问题归档/` `偏差归档/` `休眠计划/` |
| 未完成计划 / 队列里未派发的项 / 开放的 `ISS` 与未闭环的 `DEV` | 历史事实：`项目总结.md` 历史章节 / 既有 `代码修改记录/` / `操作记录/` / `证据/` |
| 规则载体（宪法段 / `工作范式.md` / 根 README / `项目清单/`） | |

**报告里必须有两节**：「本次更新的模板」逐条列 `路径 → 新版哪个模板 → 影响哪类登记`；
「本次未更新的内容」逐条列 `路径 → 原因码（已闭环 / 已冻结 / 历史事实）→ 一句话`。
不许只写「归档的不动」。要连归档正文一起改，**必须由你当轮明确发话**，
原话逐字记进当轮记录；动到冻结面的还要进审计台账。

**五条禁令**：不要拿新版模板覆盖已登记内容；不要动冻结面；不要静默改；
不要跳过差异审计直接改；**不要漏更新模板**（模板没更新 = 新版规则对下一次登记不生效）。
完整判据见该文件 §三.5。

## 二、它会做什么

### 初始化（主要用途）

```
尽调 → 判档 → 生成
```

1. **尽调**：探 VCS、探外部上游、探真实门禁命令、探已有文档体系、判规模。
   探不到的**才问用户**（六条提问，见下）。
2. **判档**：五档 —— 微型 / 轻量 / 标准 / 完整 / 重型。**宁可先低一档** ——
   框架可以长上去，多余的容器只会变成噪音。
3. **生成**：`<GOV_ROOT>/` 文档树 + 一段**宪法段**。
   宪法段落进**宿主真正会自动加载的那个文件** —— Claude Code 是 `CLAUDE.md`，
   多数其他 agent 是 `AGENTS.md`，两者都存在时写 `AGENTS.md` 并在 `CLAUDE.md` 补一行导入。
   三选一见 `templates/_宪法段模板.md` §五。

**五档速查**（完整判据与升降档信号见 `references/tier-selection.md`）：

| 档 | 适用 | 生成规模 | 关键点 |
|---|---|---|---|
| **微型** | 单文件脚本 / 周末实验 | **什么都不生成** | 给一份约 15 行的 `NEXT.md`。**装治理只会有坏处** |
| **轻量** | 单人小工具或库 | 最小集（树见 `references/tier-selection.md` §四） | 索引 + 清册 + 活跃/归档 + 队列。**4 条核心约束**（铁律仅 ③），3 步闭环 |
| **标准** | 单人/小团队主力项目 | 默认集（树见 `SKILL.md` §三） | 默认档。铁律 ③④⑤⑥，5 步闭环 |
| **完整** | 跨会话长周期产品 | 全部 | 铁律 ③④⑤⑥ + ①②（按触发），7 步闭环，五套 ID 序列 |
| **重型** | 多仓库 / 多角色 / 有发布与合规 | 全部 + 三个机制 | **角色权限矩阵 + 不可变台账 + 发布纪律** |

**必问用户的六条提问**（探不到的）：

1. 哪些目录**绝对不许改**？
2. 改动造成损失时，能接受的回滚手段是什么？
3. 谁有最终拍板权，什么情况下你会亲自发话？
4. **这套体系里，你最怕发生什么？**（答案决定生成件的侧重）
5. **产物用中文还是英文命名？**（见 `references/naming.md`）
6. **治理根放在哪？**（`<GOV_ROOT>` 的值，默认 `docs/governance`；`docs/` 被文档站占用时建议仓库根）

> **两条反直觉的建议**（都在 `tier-selection.md` 里展开）：
>
> - **微型档别装。** 你会填一份没人读的模板，而它的存在会让你以为自己有治理 —— 比没有更糟。
> - **重型档多的不是文档。** 单人项目里它解决「跨会话失忆」，重型项目里它解决
>   「多角色之间谁有权做什么」。把完整档原样放大，只会得到一份没人读的宪法。


### 审计（次要用途）

对已有框架的项目：提取它**自己声明的规则**，逐条核对实际状态，
报告三类问题——**已违反自己的规则** / **规则有但没人能执行** / **规则缺口**。
**不按本 skill 的模板去"修正"目标项目** —— 目标项目的规则载体是权威。

## 三、它装进去的是什么

六层骨架，外加一层元纪律。

| 层 | 内容 |
|---|---|
| **铁律** | 零上游改动 / 只经公开面集成 / 门禁全绿 / headless 安全 / 未落地不得声明 / **凡可能有问题一律讲清楚** |
| **权限与档位** | A–X 可改性档位 + 「默认可写 N 处」+ **「特别授权＝当轮原话点名」** |
| **ID 序列** | 五套并行编号（队列项 / 问题 / 偏差 / 操作 / 轮次），**永不复用、作废不删号** |
| **授权状态机** | **登记 → 派发 → 执行**，三段互不推定；同轮直授是合法旁路 |
| **容器分类** | 活跃 / 归档 / 休眠 / 丢弃 / 归档文档，一条分类规则 |
| **闭环仪式** | 完成宣告 3/5/7 步、N 道门、走查证据链、会话交接件 |
| **元纪律** | 规则载体多处同步 / 行号会漂 / **静默跳过=漏做** / 计数只认一处 / **实测优先于推算** / 证据不自证 |

**四条核心约束**（其余的都在为它们服务）：

1. 没有派发就没有执行权
2. 先计划后实施
3. 门禁全绿才算完成
4. 证据不自证

## 五、三个设计取舍（以及为什么）

### 1. 不打包脚本

治理实践中有三支典型的门禁工具（快照 / 死链检查 / 文档基线同步）。
**没有打包进来**，原因：

- 脚本与「路径常量走 sidecar」「纯 ASCII」「CP936 代码页」这些**本机事实**深度绑定；
- 带出去之后，用户会**以为它们开箱能用**，而实际上要先改一堆路径常量；
- 更差的情况是它们**看起来能跑但检查的是错的东西** —— 那比没有门禁更糟。

**替代**：`references/core/gates-and-holds.md` 描述**契约**（扫什么、判据是什么、日志落哪），
由目标项目自己实现。生成时门禁表只填**尽调探到的真实命令**。

> **唯一的例外：`scripts/selfcheck.py`。**
> 它检查的是**这个 skill 自己**（文档计数、目录树、模板死链、版本一致性），
> 不是给目标项目的门禁脚本。它**没有任何项目特定的路径常量**，开箱即跑：
> `python scripts/selfcheck.py`（`--quiet` 只输出失败项；退出码 0 = 全绿）。
> 每次改完这个 skill 都应该跑一次 —— 它正是这套框架里「元门禁」的自食其果。

### 2. 宪法写 `AGENTS.md` 而不是 `CLAUDE.md`

`AGENTS.md` 是跨工具的事实约定（Codex / Cursor / 其他 agent 都读它）。
写进 `AGENTS.md` 的规则，**换工具也不会丢**。
（同理，`<GOV_ROOT>/` 里的全部内容是纯 Markdown，不依赖任何特定 agent。）

### 3. 「任意项目通用」是靠**拆两层**做到的，不是靠删条款

「零上游改动 + 只经公开面集成」是这个框架最独特的部分，但它预设了「有上游」。
直接删掉会丢掉精华，直接保留会在无上游的项目里变成空话。

**解法**：拆成两层，两层都保留，只是「上游是谁」由尽调填。

| 层 | 通用表述 |
|---|---|
| 内层（边界） | 本仓库某个子树**只读**，不得编辑 |
| 外层（接口） | 只能经**已文档化**的公开面跨过这条边界 |

**没有上游的项目仍然有这条线**：`dist/`、`node_modules/`、lockfile、代码生成产物、第三方 SDK 封装层——
它们都是「只读 + 只经公开面」。这条铁律的价值在于**迫使边界被显式写下来**，
而不在于边界之外一定是别人。

## 六、用法示例

### 30 秒最小可跑（微型档：**看完就知道它会拒绝你**）

最小的一次完整运行，**产出只有一个文件**：

```
你：给这个项目建立治理框架
skill：（尽调）目录里只有 cli.py 一个源文件，140 行，没有 .git，没有测试…
        判档：微型档（1–2 个源文件 / 不打算回来维护）

你的产物：

  <项目根>/NEXT.md        ← 约 15 行，三节：下一步 / 已决定 / 坑
```

**没有 `<GOV_ROOT>/`，没有 `AGENTS.md` 宪法段，没有队列、没有台账、没有快照。**
这不是它偷懒 —— 是它的核心判断：**在这个规模上装治理只有坏处**
（你会填一份没人读的模板，而那份模板的存在会让你以为自己有治理）。

**如果它判了轻量档以上**，产物才会出现目录树，最小的一份是：
`README.md` + `工作范式.md` + `项目清单/`（含 `尽调结论.md`）+ `活跃计划/`（含 `项目总结.md`）
+ `归档计划/` + `计划队列/`（`队列总表.md` + `_队列项模板.md`），外加 `AGENTS.md` 里的 ~40 行宪法段。

## 七、已知边界

- **它不能替你做决定。** 框架的价值是让「谁有权决定什么」变得明确，
  不是替项目所有者拍板研究性/取舍性问题。
- **它对该不装的项目会说"别装"。** 判出**微型档**时，它**不生成 `<GOV_ROOT>/`**，
  只给一份约 15 行的 `NEXT.md` —— 因为给这个规模装治理**只有坏处**。
- **它的门禁需要目标项目自己的实现。** 生成的是**表**与**判据**，
  具体脚本要么项目已有，要么得自己写。
- **它的档位是可逆的。** 连续 10 轮没有新问题/偏差、某容器长期空转、只有一个人自问自答
  → 它会建议**降档**。降档的做法是标注「暂停使用 + 原因」，**不是删文件**（历史不可恢复）。
- **判据会过时。** 规则里凡是带日期戳的实测值（行号、计数、基线），
  过一段时间就会漂 —— 这正是 `anti-patterns.md` 里反复讲的「行号会漂」。**引用前先实测。**

## 八、来源

**溯源（经验从哪来）**：本 skill 的规则形态与教训原话，主要出自
**`deepseek-harness-desktop-master`（`dsh GalGame`）** 这个项目的治理实践 ——
一套在 6 万行、单人、跨会话、有外部上游的桌面产品上跑了 70+ 轮的真实体系。

> **只标项目名，不标它的内部结构**：那个项目内部的路径、目录树、文件名一律不写进本 skill。
> 溯源只需要回答「从哪个项目来的」，**不需要复制那个项目的内部事实** ——
> 那些是人家的东西，与本 skill 无关。

**归属（谁拥有它）**：**由项目所有者本人独立维护**。
它**不包含那个项目的任何内容**，**不受那个项目的任何管辖**，
**与那个项目的更新没有任何关系** —— 两条线互不驱动，各自独立迭代、独立推送。

> **为什么两者不冲突**：溯源回答「这些经验**从哪来**」，归属回答「这东西**是谁的、谁来改**」。
> 前者是**事实记录**（让教训可考），后者是**边界声明**（让迭代独立）。
> 把它们混为一谈，会得出「项目改一轮、skill 就得跟一版」这种错误推论。

## 九、改这个 skill 的流程（自维护）

**这个 skill 的全部内容都是文档，而文档会静默腐化 —— 所以「改完怎么确认没改坏」必须写死在这里。**

**固定四步**：

1. **改** —— 一次只改一类问题，改完立刻进入第 2 步。
2. **跑自检** —— `python scripts/selfcheck.py`。**必须 `failed=0` 才继续**；
   有失败项就修到全绿（`--quiet` 只打印失败项，适合自己看）。
3. **升版** —— 改了内容就动 `SKILL.md` frontmatter 的 `metadata.version`，并在 §十 记一行「为什么升版」。
   **两处必须同步**（自检的 `version-consistency` 会抓不一致）。
   **每次推送前都要升版**：只要这次提交改了任何一个 `.md` 或 `scripts/`，就必须升
   —— **不许拿「改动很小」当不升版的理由**。
   **兼容变更递增次版本**（`1.6.0` → `1.6.1`）；**不兼容变更递增主版本**（→ `2.0.0`）并写迁移步骤。
   只改 `.gitignore` / `.gitattributes` 这类不影响内容的文件时才可以不升。
4. **写一句实态** —— 在 §十 对应的版本行写清「改了什么、为什么」。

**三条纪律**：

- **不许只改不跑自检** —— 已经吃过一次「同一条规则在两个载体里只改了一处」的事故（见 §十 1.0.0 条目）。
- **不许新增无人引用的文件** —— 自检的 `orphan-files` 会抓；真需要独立文件就同时加进目录树与引用。
- **不许让旧写法回流** —— 上一轮修掉的形态（旧式破折号标记、未核实的目录数）
  已在自检的 `stale-phrases` / `marker-vocabulary` 里登记，重新出现即红。
  （反例本身**不要原样写进任何 md** —— 自检会把它当成真违规。）

> **备份**：这个 skill 目录**可能不在目标项目的快照 / 门禁范围内**（取决于那个项目怎么配扫描面）。
> 也就是说**它未必有自动保护**。**改之前请自行确认有一份可回退的副本**
> （你自己的 git 仓库 / 版本管理 / 备份目录 / 打包 zip）。
