# buer-pro-max

> 把一套**跨会话的项目治理体系**装进任意仓库的 Claude skill。
>
> 它解决的不是「怎么写文档」，而是**「下一个会话凭什么知道这一轮发生了什么、下一步该做什么」**。
>
> **独立产物**：不包含任何具体项目的内容，独立迭代，与任何项目的更新节奏无关。
> 其中的规则形态与教训来自长期的真实开发实践 —— **主要出自
> `deepseek-harness-desktop-master`（`dsh GalGame`）的治理实践**（70+ 轮），
> 踩出来的坑都在 `references/anti-patterns.md` 里。
>
> **溯源 ≠ 归属**：标明经验从哪来，是为了让每条教训可考、可追；
> 但 skill 本身**不归那个项目管理**，也不随它演进。

## 一、安装

把整个文件夹拷进 skills 目录即可。

```sh
# 用户级（对所有项目生效）
cp -r buer-pro-max ~/.claude/skills/

# 或项目级（只对该项目生效）
cp -r buer-pro-max <项目根>/.claude/skills/
```

Windows：

```powershell
Copy-Item -Recurse -Force buer-pro-max "$env:USERPROFILE\.claude\skills\buer-pro-max"
```

装好后在新会话里说 **"给这个项目建立治理"** 或 **"建立治理框架"** 即可触发。

**其他 agent（Codex / Cursor / 其他）怎么装**：上面的 `.claude/skills/` 是 Claude Code 的约定。
换宿主时**不要猜路径** —— 两种可靠做法：
1. 把整个 `buer-pro-max/` 放到该工具**约定读取规则/技能的位置**（查它自己的文档）；
2. 或**直接把 `SKILL.md` 的内容作为规范喂给它**，并把 `references/` 一起放在可达位置。

**Codex** 的约定位置是 `$CODEX_HOME/skills/`（默认 `~/.codex/skills/`）。

> **运行期无依赖，维护期需 Python 3**：这个 skill 被读取时是纯 Markdown（无依赖）；
> 只有**维护它自己**时才需要 Python 3 跑 `scripts/selfcheck.py`。

> **产物不依赖 Claude Code**（skill 本身是 Claude Code 格式的，这一条要说清）：
> 本 skill 的**产物**是写进 `AGENTS.md` 的宪法段 + `<GOV_ROOT>/` 文档树，
> 两者都是纯文本。任何读 `AGENTS.md` 约定的工具（Codex / Cursor / 其他 agent）都能吃到同一份规则。
> **注意区分**：产物跨工具通用 ✅；**读取这个 skill 的入口**（`SKILL.md`）是 Claude Code 的目录约定 ❌。

## 二、它会做什么

### 初始化（主要用途）

```
尽调 → 判档 → 生成
```

1. **尽调**：探 VCS、探外部上游、探真实门禁命令、探已有文档体系、判规模。
   探不到的**才问用户**（六条提问，见下）。
2. **判档**：五档 —— 微型 / 轻量 / 标准 / 完整 / 重型。**宁可先低一档** ——
   框架可以长上去，多余的容器只会变成噪音。
3. **生成**：`<GOV_ROOT>/` 文档树 + 一段写进 `AGENTS.md` 的**宪法段**。

**五档速查**（完整判据与升降档信号见 `references/tier-selection.md`）：

| 档 | 适用 | 生成规模 | 关键点 |
|---|---|---|---|
| **微型** | 单文件脚本 / 周末实验 | **什么都不生成** | 给一份约 15 行的 `NEXT.md`。**装治理只会有坏处** |
| **轻量** | 单人小工具或库 | 最小集（树见 `references/tier-selection.md` §四） | 只装三样：**清册 + 排队 + 归档**。3 条核心约束（铁律仅 ③），3 步闭环 |
| **标准** | 单人/小团队主力项目 | 默认集（树见 `SKILL.md` §三） | 默认档。铁律 ③④⑤⑥，5 步闭环 |
| **完整** | 跨会话长周期产品 | 全部 | 铁律 ③④⑤⑥ + ①②（按触发），7 步闭环，四套 ID 序列 |
| **重型** | 多仓库 / 多角色 / 有发布与合规 | 全部 + 三个机制 | **角色权限矩阵 + 不可变台账 + 发布纪律** |

**必问用户的六条提问**（探不到的）：

1. 哪些目录**绝对不许改**？
2. 改动造成损失时，能接受的回滚手段是什么？
3. 谁有最终拍板权，什么情况下你会亲自发话？
4. **这套体系里，你最怕发生什么？**（答案决定生成件的侧重）
5. **产物用中文还是英文命名？**（见 `references/naming.md`）
6. **治理根放在哪？**（`<GOV_ROOT>` 的值，默认 `docs/governance`；`docs/` 被文档站占用时建议仓库根）

> **两条反直觉的建议**（都在 `tier-selection.md` 里展开）：
>
> - **微型档别装。** 你会填一份没人读的模板，而它的存在会让你以为自己有治理 —— 比没有更糟。
> - **重型档多的不是文档。** 单人项目里它解决「跨会话失忆」，重型项目里它解决
>   「多角色之间谁有权做什么」。把完整档原样放大，只会得到一份没人读的宪法。


### 审计（次要用途）

对已有框架的项目：提取它**自己声明的规则**，逐条核对实际状态，
报告三类问题——**已违反自己的规则** / **规则有但没人能执行** / **规则缺口**。
**不按本 skill 的模板去"修正"目标项目** —— 目标项目的规则载体是权威。

## 三、它装进去的是什么

六层骨架，外加一层元纪律。

| 层 | 内容 |
|---|---|
| **铁律** | 零上游改动 / 只经公开面集成 / 门禁全绿 / headless 安全 / 未落地不得声明 / **凡可能有问题一律讲清楚** |
| **权限与档位** | A–X 可改性档位 + 「默认可写 N 处」+ **「特别授权＝当轮原话点名」** |
| **ID 序列** | 四套并行编号（队列项 / 问题 / 偏差 / 轮次），**永不复用、作废不删号** |
| **授权状态机** | **登记 → 派发 → 执行**，三段互不推定；同轮直授是合法旁路 |
| **容器分类** | 活跃 / 归档 / 休眠 / 丢弃 / 归档文档，一条分类规则 |
| **闭环仪式** | 完成宣告 3/5/7 步、N 道门、走查证据链、会话交接件 |
| **元纪律** | 规则载体多处同步 / 行号会漂 / **静默跳过=漏做** / 计数只认一处 / 证据不自证 |

**四条核心约束**（其余的都在为它们服务）：

1. 没有派发就没有执行权
2. 先计划后实施
3. 门禁全绿才算完成
4. 证据不自证

## 五、三个设计取舍（以及为什么）

### 1. 不打包脚本

治理实践中有三支典型的门禁工具（快照 / 死链检查 / 文档基线同步）。
**没有打包进来**，原因：

- 脚本与「路径常量走 sidecar」「纯 ASCII」「CP936 代码页」这些**本机事实**深度绑定；
- 带出去之后，用户会**以为它们开箱能用**，而实际上要先改一堆路径常量；
- 更差的情况是它们**看起来能跑但检查的是错的东西** —— 那比没有门禁更糟。

**替代**：`references/core/gates-and-holds.md` 描述**契约**（扫什么、判据是什么、日志落哪），
由目标项目自己实现。生成时门禁表只填**尽调探到的真实命令**。

> **唯一的例外：`scripts/selfcheck.py`。**
> 它检查的是**这个 skill 自己**（文档计数、目录树、模板死链、版本一致性），
> 不是给目标项目的门禁脚本。它**没有任何项目特定的路径常量**，开箱即跑：
> `python scripts/selfcheck.py`（`--quiet` 只输出失败项；退出码 0 = 全绿）。
> 每次改完这个 skill 都应该跑一次 —— 它正是这套框架里「元门禁」的自食其果。

### 2. 宪法写 `AGENTS.md` 而不是 `CLAUDE.md`

`AGENTS.md` 是跨工具的事实约定（Codex / Cursor / 其他 agent 都读它）。
写进 `AGENTS.md` 的规则，**换工具也不会丢**。
（同理，`<GOV_ROOT>/` 里的全部内容是纯 Markdown，不依赖任何特定 agent。）

### 3. 「任意项目通用」是靠**拆两层**做到的，不是靠删条款

「零上游改动 + 只经公开面集成」是这个框架最独特的部分，但它预设了「有上游」。
直接删掉会丢掉精华，直接保留会在无上游的项目里变成空话。

**解法**：拆成两层，两层都保留，只是「上游是谁」由尽调填。

| 层 | 通用表述 |
|---|---|
| 内层（边界） | 本仓库某个子树**只读**，不得编辑 |
| 外层（接口） | 只能经**已文档化**的公开面跨过这条边界 |

**没有上游的项目仍然有这条线**：`dist/`、`node_modules/`、lockfile、代码生成产物、第三方 SDK 封装层——
它们都是「只读 + 只经公开面」。这条铁律的价值在于**迫使边界被显式写下来**，
而不在于边界之外一定是别人。

## 六、用法示例

### 30 秒最小可跑（微型档：**看完就知道它会拒绝你**）

最小的一次完整运行，**产出只有一个文件**：

```
你：给这个项目建立治理框架
skill：（尽调）目录里只有 cli.py 一个源文件，140 行，没有 .git，没有测试…
        判档：微型档（1–2 个源文件 / 不打算回来维护）
        → 按 SKILL.md §三：「微型档只生成一份 NEXT.md，不生成 <GOV_ROOT>/」
你的产物：

  <项目根>/NEXT.md        ← 约 15 行，三节：下一步 / 已决定 / 坑
```

**没有 `<GOV_ROOT>/`，没有 `AGENTS.md` 宪法段，没有队列、没有台账、没有快照。**
这不是它偷懒 —— 是它的核心判断：**在这个规模上装治理只有坏处**
（你会填一份没人读的模板，而那份模板的存在会让你以为自己有治理）。

**如果它判了轻量档以上**，产物才会出现目录树，最小的一份是：
`README.md` + `工作范式.md` + `项目清单/`（含 `尽调结论.md`）+ `活跃计划/`（含 `项目总结.md`）
+ `归档计划/` + `计划队列/`（`队列总表.md` + `_队列项模板.md`），外加 `AGENTS.md` 里的 ~40 行宪法段。

### 一个标准档项目的完整对话

```
你：给这个项目建立治理框架
skill：（尽调）探到 Node + pnpm，有 .git，无 submodule，src/ 4.2k 行…
        探不到的问你这四条提问
你：不许改 vendor/ 和 dist/；回滚靠 git；只有我拍板；最怕改了不该改的
skill：（生成）<GOV_ROOT>/ 全套 + AGENTS.md 宪法段
        门禁表填的是你 package.json 里真实存在的 lint/test/build
        vendor/ 与 dist/ 进了只读名单与硬停清单
```

之后日常是这样用的：

```
你：登记一个问题 —— 分页在空列表时会返回 NaN
skill：在 <GOV_ROOT>/问题记录/ 建 ISS-001-….md，并在队列总表更新计数

你：派发它
skill：把队列项移动到活跃计划/、改名、追加「派发补充」节（含执行顺序与硬停）

你：（做完后）闭环
skill：走完成宣告 N 步 —— 勾选计划、追加轮次章节、更新索引、归档并修全部路径引用、
        同步代码地图；生成会话交接件
```

## 七、已知边界

- **它不能替你做决定。** 框架的价值是让「谁有权决定什么」变得明确，
  不是替项目所有者拍板研究性/取舍性问题。
- **它对该不装的项目会说"别装"。** 判出**微型档**时，它**不生成 `<GOV_ROOT>/`**，
  只给一份约 15 行的 `NEXT.md` —— 因为给这个规模装治理**只有坏处**。
- **它的门禁需要目标项目自己的实现。** 生成的是**表**与**判据**，
  具体脚本要么项目已有，要么得自己写。
- **它的档位是可逆的。** 连续 10 轮没有新问题/偏差、某容器长期空转、只有一个人自问自答
  → 它会建议**降档**。降档的做法是标注「暂停使用 + 原因」，**不是删文件**（历史不可恢复）。
- **判据会过时。** 规则里凡是带日期戳的实测值（行号、计数、基线），
  过一段时间就会漂 —— 这正是 `anti-patterns.md` 里反复讲的「行号会漂」。**引用前先实测。**

## 八、来源

**溯源（经验从哪来）**：本 skill 的规则形态与教训原话，主要出自
**`deepseek-harness-desktop-master`（`dsh GalGame`）** 这个项目的治理实践 ——
一套在 6 万行、单人、跨会话、有外部上游的桌面产品上跑了 70+ 轮的真实体系。

> **只标项目名，不标它的内部结构**：那个项目内部的路径、目录树、文件名一律不写进本 skill。
> 溯源只需要回答「从哪个项目来的」，**不需要复制那个项目的内部事实** ——
> 那些是人家的东西，与本 skill 无关。

**归属（谁拥有它）**：**由项目所有者本人独立维护**。
它**不包含那个项目的任何内容**，**不受那个项目的任何管辖**，
**与那个项目的更新没有任何关系** —— 两条线互不驱动，各自独立迭代、独立推送。

> **为什么两者不冲突**：溯源回答「这些经验**从哪来**」，归属回答「这东西**是谁的、谁来改**」。
> 前者是**事实记录**（让教训可考），后者是**边界声明**（让迭代独立）。
> 把它们混为一谈，会得出「项目改一轮、skill 就得跟一版」这种错误推论。

**许可证**：**MIT**（见 `LICENSE`）。

## 九、改这个 skill 的流程（自维护）

**这个 skill 的全部内容都是文档，而文档会静默腐化 —— 所以「改完怎么确认没改坏」必须写死在这里。**

**固定四步**：

1. **改** —— 一次只改一类问题，改完立刻进入第 2 步。
2. **跑自检** —— `python scripts/selfcheck.py`。**必须 `failed=0` 才继续**；
   有失败项就修到全绿（`--quiet` 只打印失败项，适合自己看）。
3. **升版** —— 改了内容就动 `SKILL.md` frontmatter 的 `metadata.version`，并在 §十 记一行「为什么升版」。
   **两处必须同步**（自检的 `version-consistency` 会抓不一致）。
4. **写一句实态** —— 在 §十 对应的版本行写清「改了什么、为什么」。

**三条纪律**：

- **不许只改不跑自检** —— 已经吃过一次「同一条规则在两个载体里只改了一处」的事故（见 §十 1.0.0 条目）。
- **不许新增无人引用的文件** —— 自检的 `orphan-files` 会抓；真需要独立文件就同时加进目录树与引用。
- **不许让旧写法回流** —— 上一轮修掉的形态（旧式破折号标记、未核实的目录数）
  已在自检的 `stale-phrases` / `marker-vocabulary` 里登记，重新出现即红。
  （反例本身**不要原样写进任何 md** —— 自检会把它当成真违规。）

> **备份**：这个 skill 目录**可能不在目标项目的快照 / 门禁范围内**（取决于那个项目怎么配扫描面）。
> 也就是说**它未必有自动保护**。**改之前请自行确认有一份可回退的副本**
> （你自己的 git 仓库 / 版本管理 / 备份目录 / 打包 zip）。
