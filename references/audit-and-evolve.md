# 审计与演进模式

> 本文件是 `SKILL.md` 的展开。**路由在 `SKILL.md`，细则在这里。**
> 读它之前先看 `SKILL.md` 对应那一节的一句话摘要。

---

## 一、审计模式（对已有框架）

对这个 skill 生成过的、或任何自带治理体系的仓库。

1. 读目标项目的规则载体，**提取出它自己声明的规则**（不是本 skill 的规则）。
2. 按下面清单逐项核对。
3. 报告分三类输出：**已违反自己的规则** / **规则有但没人能执行** / **规则缺口**。
4. **不要按本 skill 的模板去「修正」目标项目**。目标项目的规则载体是权威；
   只报告偏离，改动等用户发话。

### 审计清单（逐项过，每项给证据）

**A. 计数与真源**
- [ ] 总表里的计数 vs 实际条目数（**逐个容器数一遍，不抽检**）
- [ ] 同一个数字是否在多处各写了一份（→ 分叉风险）
- [ ] 「下一个可用 ID」是否正确（**只看权威落点，不看全仓 grep 命中**）

**B. 状态机**
- [ ] 有无**无派发件的直接改动**（查记录里的「同轮直授」是否都登记了偏差）
- [ ] 有无**派发件写了但没开工**却已计入「执行中」
- [ ] 有无计划的**状态与其容器矛盾**（已闭环却还在活跃 / 未完成却已归档）

**C. 闭环仪式**
- [ ] 最近 N 轮**逐轮记录章节是否齐全**（章节号与轮次号是否一一对应）
- [ ] 「最近 N 轮」状态块是否是**定长窗口**（有没有退化成状态日志）
- [ ] **代码地图三节**的日期戳是否随轮更新；有无静默跳过（该有声明行而没有）
- [ ] 归档时**路径引用是否都修了**（跑引用完整性门禁）
- [ ] 走查证据的 `verdict` 是否**由执行轮自己打了 PASS**（这是违规）

**D. 冻结面**
- [ ] 冻结容器里有没有被改写的痕迹（对比历史快照/指纹）
- [ ] 更正是否走了「就地更正 + 注记」而不是静默改写

**E. 门禁**
- [ ] 门禁表里有没有**不存在的命令**（→ 名存实亡，且没人会发现）
- [ ] 有无**空行**（「查过没有」与「根本没查」无法区分）
- [ ] 阈值/豁免行有没有被放宽过（对比历史记录）
- [ ] 环境性失败有没有**如实归因**，还是被粉饰

**F. 规则缺口**
- [ ] 反复出问题的事，有没有规则覆盖？**没有 → 这是缺口，不是偶发**
- [ ] 偏差里「复读最多的同一条」是什么？（同一根因反复出现 = 结构性问题）
- [ ] 有没有规则**只写在文档里、没有任何门禁或单测兜住**（→ 它会在第三轮消失）

**G. 文档卫生**
- [ ] 受治理文档有无**重复的同一级标题**（文件被复制整份的指纹）
- [ ] 每条规则是否**给判据**，还是只写了态度
- [ ] 引用里的 `file:line` 有没有**实测过**（抽查几处，行号漂没漂）

### 报告格式

```markdown
## 审计结论（<日期>）

**范围**：<审计了哪些容器/文档>
**总评**：<一句话；体系是活的还是在腐化>

### 一、已违反自己的规则
| # | 规则 | 实际状态 | 证据 | 严重度 |

### 二、规则有但没人能执行
| # | 规则 | 为什么执行不了 | 建议 |

### 三、规则缺口
| # | 现象 | 频次/证据 | 建议新增的规则 |

**未纳入本次审计的范围**：<显式列出 —— 没查的东西不等于没问题>
```

**最后一行很重要**：审计报告里**「没查的部分」必须写出来**，
否则读者会把「全绿」理解成「全都查过且全对」。

## 二、演进：加容器 / 升档 / 降档 / 改名

框架是**可以长的**，但长法有纪律。四种动作都**不改历史**：

| 动作 | 什么时候 | 步骤 |
|---|---|---|
| **加容器** | 尽调后才发现需要某个可选容器；或项目长出了新的一类东西 | ① 先写该容器的 `README.md`（**放什么 / 什么时候进 / 什么时候出 / 不在这里放什么**）→ ② 加进 `项目清单/README.md` 的**结构视图**与 `<GOV_ROOT>/README.md` 的容器一览 → ③ 在当轮记录里写明「**为什么加**」与触发信号 → ④ 登记一条留痕（有 `DEV` 序列则登记，否则写进队列总表注记区），不要静默加 |
| **升档** | 命中 `tier-selection.md` §六 的任一升档信号 | ① 对照 `tier-selection.md` §一 的档位表列出**本档缺哪些容器 / 序列 / 仪式步骤** → ② **逐个补**，用同一套模板（不要发明新格式）→ ③ 改 `<GOV_ROOT>/README.md` 的「档位」节 + 补「为什么不选更高档」的理由 → ④ 门槛类规则（标记为「必选 · 标准档起」的那些）此时才生效 |
| **降档** | 命中降档信号（连续 10 轮无 `ISS`/`DEV`、容器长期空转、单人自问自答） | ① **不删任何文件** → ② 在该容器 `README.md` 写一行「**本容器 `<日期>` 起暂停使用 —— 原因：`<…>`。历史记录保留，不再新增。**」→ ③ 改档位节 → ④ 登记一条 `DEV`（说明为什么降） |
| **改名**（中文 ↔ 英文，或换治理根路径） | 用户反悔了初始化时选的命名方案 | ① **整批**改名（`naming.md` §三 对照表），**不要逐个文件慢慢改** → ② 修**全部**引用：宪法段、`<GOV_ROOT>/README.md` 阅读顺序、`项目清单/` 结构视图、各容器 README → ③ 跑一次死链核对 → ④ 登记一条 `DEV`（说明为什么改、改了哪些载体） |

**三条禁令**（否则演进会演变成腐化）：

1. **降档不删文件** —— 历史记录不可恢复，删掉它等于抹掉「当时到底发生了什么」。
2. **升档不跳步** —— 不能"直接从轻量跳到重型"，中间档的容器与仪式必须补齐；跳过的那一档会在第一次出事时暴露。
3. **演进动作本身要留痕** —— 加/升/降都是**结构变化**，必须进当轮记录与 `DEV`。**只改文件不记录 = 下一个会话不知道框架曾经变过。**

**判据**：演进完成后，`项目清单/README.md` 的结构视图、`<GOV_ROOT>/README.md` 的容器一览、以及实际目录树**三者必须一致** —— 不一致就是演进做了一半。

## 三、版本对齐（把已有的治理树对齐到新版 skill）

> **这一节回答一个 `git pull` 回答不了的问题：skill 更新了，我项目里那棵已经生成的树怎么办？**

**核心判据：`git pull` 只更新 skill，不动 `<GOV_ROOT>/`。** 两者是独立产物
（`README.md` §三「独立产物」）。所以「对齐」不是升级动作，是**一次审计 + 逐条裁决**。

> **⚠ 本流程的第一条硬规则在 §3**：**模板必须更新**（下一次登记才按新规则生效），
> 但**已登记的归档正文一个字都不改** —— 已完成的归档计划、已关闭的问题与偏差、
> 已冻结的文档不进更新，并且每一项跳过都要写明原因码。
> **先读完 §3 再动手** —— 它决定了 §2 第 3 步审计的语料范围。

### 1. 三种情况，别混成一种

| 你观察到什么 | 这是哪种问题 | 走哪节 |
|---|---|---|
| 新版 skill 改了措辞 / 补了规则 / 修了模板里的错 | **规则版本落后** | 本节 §三.2「对齐」 |
| 现有树的**结构**不够用（缺容器 / 档位不对 / 想改名） | **演进** | 上面「演进」表 |
| 现有树**违反了自己声明的规则**（例如偏差挤在单文件里） | **审计 → 修复** | 本节 §一 + 修复后留痕 |

**判断顺序**：先做 §一 的审计 —— 如果违反的是**目标项目自己的规则**，那是审计问题，
不是版本落后；只有当**规则载体本身**与新版冲突时，才走对齐。

### 2. 对齐的七步

1. **拉取并确认版本**：`git -C <skills 目录> pull --ff-only` → 查 `metadata.version`
   → `python scripts/selfcheck.py` 必须 `failed=0`（`README.md` §一·补）。**拉到的若是发布前提交，先切回去。**
2. **圈定作用域**：**先判「哪些算在途、哪些是模板、哪些是已登记正文」**（§3.1）——
   **模板无条件进更新**（它们是生产规则，决定下一次登记长什么样）；
   已登记的正文里，只有在途条目进更新，已闭环 / 已冻结的一律划到作用域外，
   并在报告里逐条记下原因码（§3.2）。**这一步在差异审计之前做**，否则审计会把
   归档正文也列进「待改」，下一轮就会被改。
3. **差异审计，不重新生成**：让 agent 读新版 `references/` 与 `templates/`，
   对比**作用域内**已经生成的规则载体，按 §一 的三类输出报告。
   **明确要求它只报告、不改动** —— 否则它会顺手「修正」你的项目。
4. **逐条裁决**：采纳 / 不采纳 / 押后。**每条都要有记录** ——
   不采纳的要写理由，否则下一轮会被重新提出（同 `_执行偏差README` §五「明确不做」的纪律）。
5. **只改规则载体，保留项目自己的东西**：目标项目的措辞、历史、已填的占位符都是资产。
   对齐是**改规则**，不是**换文件**。
6. **涉及结构变化 → 转演进模式**：加容器 / 升档 / 降档 / 改名按上面那四行走，
   **不要在对齐流程里顺手做结构变更** —— 两件事混在一起，出问题时无法归因。
7. **留痕**：每次对齐登记一条偏差（`DEV-NNN`；无该序列的档位写进队列总表注记区），
   写明「对齐到 skill `<版本>`，改了哪几个载体、哪几条规则、**哪些按规则没动及原因码**」。

### 3. 更新范围：**模板要更新，归档正文不动**

> **这是对齐流程的第一条硬规则，不是可选项。** 它区分两样**看起来都是「更新」**的东西：
>
> | | 动什么 | 什么时候影响 |
> |---|---|---|
> | **模板**（`_问题模板.md` / `_偏差模板.md` / `_记录模板.md` / `_队列项模板.md` / 各容器 README 模板 → 落到项目里的对应文件） | ✅ **必须更新** | **下一次登记**才生效 |
> | **已登记的正文**（归档计划 / 已关闭的 `ISS` / 已闭环的 `DEV` / 归档文档） | ❌ **一个字都不改** | 永远 |
>
> **一句话**：**规则往后生效，历史原样保留。** 模板更新是为了**下一次**按新规则登记；
> 它不是把旧登记翻新的许可。
>
> 把这两件事混起来的后果：要么「模板没更新 → 下一次登记又按旧规则写」，
> 要么「连归档正文一起刷 → 审计链断掉」。两种都是错的，而且方向相反。

**为什么模板必须更新**：模板是**生产规则**。模板不更新，新版规则对滚动的事一条都落不了地 ——
下一个会话打开 `_偏差模板.md` 复制出来的还是旧格式，于是「skill 升级了但行为没变」。
**判据：模板更新后，下一次登记产出的文件应当符合新规则**，而不是「旧文件被改成了新样子」。

**为什么归档正文不能动**：已闭环的记录是**证据与历史**。改写它们等于篡改账本
（`anti-patterns.md` #13），审计链当场断掉，而且与「归档容器只读、不重叠、不留副本」
直接冲突（`plan-containers.md` §三、各归档容器的 README）。
新版模板再正确，也不是重写历史的理由。

#### 3.1 作用域：谁进更新、谁不动

| 容器 / 内容 | 默认是否更新 | 说明 |
|---|---|---|
| **模板文件**：`计划队列/_队列项模板.md`、`问题记录/_问题模板.md`、`执行偏差/_偏差模板.md`、`代码修改记录/_记录模板.md`、各容器 `README.md` 里由模板生成的部分 | ✅ **必须更新** | **这是本条规则的核心** —— 它们决定下一次登记长什么样 |
| `活跃计划/` 的**未完成部分** | ✅ 更新 | 按新规则补字段、补步骤；**已完成的小节保持原样**，只对未完成部分生效 |
| `计划队列/` 的未派发 / 未完成项 | ✅ 更新 | 队列项的格式与字段按新规则补齐 |
| `问题记录/` 中**状态为开放**的 | ✅ 更新 | 关闭后再归档时适用 `问题归档/` 那行 |
| `执行偏差/` 中**未闭环**的 | ✅ 更新 | 格式与六类判定按新规则；闭环后进 `偏差归档/` 不动 |
| 规则载体：宪法段 / `工作范式.md` / `<GOV_ROOT>/README.md` / `项目清单/` | ✅ 更新 | **这正是「对齐」要改的东西** —— 规则本身必须跟上新版 |
| `归档计划/` `归档文档/` `问题归档/` `偏差归档/` `休眠计划/` 里的**正文** | ❌ **不改** | 已闭环或已冻结。触发信号：该条目**已走完闭环仪式 / 已被取代 / 用户已明确暂缓** |
| `项目总结.md` 的历史章节、既有 `代码修改记录/` 的条目、既有 `操作记录/` 的条目、既有 `证据/` | ❌ **不改** | 逐轮叙事与证据是**当时的事实**，不是可以翻新的规则 |

> **容易搞错的一条**：`归档计划/` `问题归档/` `偏差归档/` 里**通常没有模板**。
> 如果某个归档容器里确实带着模板副本（例如早期的 `归档文档/_某模板.md`），
> **不动它** —— 归档容器是冻结面，它的模板副本是当时那份，本身也是历史。

#### 3.2 必须附带「不更新的原因」

对齐报告与留痕里，**每一项被跳过的内容都要写出原因**，按下面三种之一：

| 原因码 | 含义 | 适用 |
|---|---|---|
| **已闭环** | 该条目已走完全部闭环仪式，改动即篡改历史 | `归档计划/` 的全部、`问题归档/`、`偏差归档/` |
| **已冻结** | 容器声明为只读，唯一例外是路径与行号的事实性更正 | `休眠计划/`、`归档文档/`、归档子目录 |
| **历史事实** | 逐轮叙事 / 证据 / 既有记录描述的是当轮实况，不随后续规则变化而改写 | `项目总结.md`、`代码修改记录/`、`操作记录/`、`证据/` |

**报告里必须同时有两节，缺一不可**：

- **「本次更新的模板」** —— 逐条列出 `模板路径 → 对应 skill 新版的哪个模板 → 影响哪类下一次登记`；
- **「本次未更新的内容」** —— 逐条列出 `路径 → 原因码 → 一句话`。

**不要只写「已归档的不动」** —— 那让人无法区分「按规则跳过」与「忘了」。
这与 `self-check.md` 的「静默跳过 = 漏做」是同一条纪律。

#### 3.3 用户明确要求一起更新时

**唯一例外是用户当轮明确发话**（「把归档的也一起更新」这类原话）。此时：

1. **逐字记录原话**进当轮记录的「拍板落档」节 —— 概括会丢掉限定条件。
2. **限定范围**：用户说的是「全部」还是「某一批」？按原话执行，不扩大。
3. **冻结面仍然留痕**：越过冻结面的改动进 `审计台账.md`（重型档需**双签**），
   并在被改文件里**注记**「<日期> 按用户原话对齐到 skill <版本>」——
   **不改写就等于没有发生过**，但**不改写也不能让它看起来像原样**。
4. **不做**：用户没发话时，**不得**因为「新版模板更好」而顺手更新已闭环内容。

> **判据**：对齐结束后，`归档计划/` `归档文档/` `问题归档/` `偏差归档/` `休眠计划/`
> 的 `git diff` 必须为空（用户明确授权的那次除外，且那次要有留痕）；
> **同时**，`_问题模板.md` `_偏差模板.md` `_记录模板.md` `_队列项模板.md` 这几份
> **必须出现在「本次更新的模板」清单里** —— 它们没进清单，说明模板漏更新了。

### 4. 五条禁令

1. **不要拿新版模板「整棵覆盖」生成树。** 覆盖会抹掉项目自己的历史、措辞与已填的占位符，
   而且**看起来像升级成功** —— 这是这套体系里最难被发现的一类损坏。
   **注意别读反**：模板**文件本身必须更新**（§3.1 第一行），被禁止的是拿模板去覆盖
   **已登记的内容**、或整目录替换整棵治理树。
2. **不要动冻结面。** `归档计划/` `问题归档/` `偏差归档/` `归档文档/` 的正文只读；
   唯一例外是路径与行号的事实性更正（就地注记），以及 §3.3 的**用户当轮明确授权**。
3. **不要静默改。** 任何规则变化都留痕 —— 「只改文件不记录 = 下一个会话不知道框架曾经变过」。
4. **不要跳过第 2 步直接改。** 没有差异报告就开始改，你会同时引入新规则和旧规则的混合版本。
5. **不要漏更新模板。** 模板没进「本次更新的模板」清单 = 新版规则对**下一次登记**不生效，
   等于这次对齐白做。**模板更新是这一流程的产出，不是可选项。**

### 5. 判据

主体必须**同时**成立：

- `项目清单/README.md` 的结构视图 = `<GOV_ROOT>/README.md` 的容器一览 = 实际目录树；
- 引用完整性门禁 `dead=0`；
- 裁决表里每一条都有「采纳 / 不采纳（含理由）/ 押后」；
- 有一条留痕记录，写明了对齐到的 skill 版本；
- **「本次更新的模板」一节存在且非空** —— 该更新的模板一份都没漏；
- **归档容器与已冻结内容的 `git diff` 为空**（用户明确授权的那次除外，且该次有留痕）。

**其中一条不成立 = 对齐做了一半。** 半对齐比不对齐更危险：它让新旧规则同时生效，
而没有任何索引能看出哪些是新的、哪些是旧的。
