## 一、审计模式（对已有框架）

对这个 skill 生成过的、或任何自带治理体系的仓库。

1. 读目标项目的规则载体，**提取出它自己声明的规则**（不是本 skill 的规则）。
2. 按下面清单逐项核对。
3. 报告分三类输出：**已违反自己的规则** / **规则有但没人能执行** / **规则缺口**。
4. **不要按本 skill 的模板去「修正」目标项目**。目标项目的规则载体是权威；
   只报告偏离，改动等用户发话。

### 审计清单（逐项过，每项给证据）

**A. 计数与真源**
- [ ] 总表里的计数 vs 实际条目数（**逐个容器数一遍，不抽检**）
- [ ] 同一个数字是否在多处各写了一份（→ 分叉风险）
- [ ] 「下一个可用 ID」是否正确（**只看权威落点，不看全仓 grep 命中**）

**B. 状态机**
- [ ] 有无**无派发件的直接改动**（查记录里的「同轮直授」是否都登记了偏差）
- [ ] 有无**派发件写了但没开工**却已计入「执行中」
- [ ] 有无计划的**状态与其容器矛盾**（已闭环却还在活跃 / 未完成却已归档）

**C. 闭环仪式**
- [ ] 最近 N 轮**逐轮记录章节是否齐全**（章节号与轮次号是否一一对应）
- [ ] 「最近 N 轮」状态块是否是**定长窗口**（有没有退化成状态日志）
- [ ] **代码地图三节**的日期戳是否随轮更新；有无静默跳过（该有声明行而没有）
- [ ] 归档时**路径引用是否都修了**（跑引用完整性门禁）
- [ ] 走查证据的 `verdict` 是否**由执行轮自己打了 PASS**（这是违规）

**D. 冻结面**
- [ ] 冻结容器里有没有被改写的痕迹（对比历史快照/指纹）
- [ ] 更正是否走了「就地更正 + 注记」而不是静默改写

**E. 门禁**
- [ ] 门禁表里有没有**不存在的命令**（→ 名存实亡，且没人会发现）
- [ ] 有无**空行**（「查过没有」与「根本没查」无法区分）
- [ ] 阈值/豁免行有没有被放宽过（对比历史记录）
- [ ] 环境性失败有没有**如实归因**，还是被粉饰

**F. 规则缺口**
- [ ] 反复出问题的事，有没有规则覆盖？**没有 → 这是缺口，不是偶发**
- [ ] 偏差里「复读最多的同一条」是什么？（同一根因反复出现 = 结构性问题）
- [ ] 有没有规则**只写在文档里、没有任何门禁或单测兜住**（→ 它会在第三轮消失）

**G. 文档卫生**
- [ ] 受治理文档有无**重复的同一级标题**（文件被复制整份的指纹）
- [ ] 每条规则是否**给判据**，还是只写了态度
- [ ] 引用里的 `file:line` 有没有**实测过**（抽查几处，行号漂没漂）

### 报告格式

```markdown
## 审计结论（<日期>）

**范围**：<审计了哪些容器/文档>
**总评**：<一句话；体系是活的还是在腐化>

### 一、已违反自己的规则
| # | 规则 | 实际状态 | 证据 | 严重度 |

### 二、规则有但没人能执行
| # | 规则 | 为什么执行不了 | 建议 |

### 三、规则缺口
| # | 现象 | 频次/证据 | 建议新增的规则 |

**未纳入本次审计的范围**：<显式列出 —— 没查的东西不等于没问题>
```

**最后一行很重要**：审计报告里**「没查的部分」必须写出来**，
否则读者会把「全绿」理解成「全都查过且全对」。

### 演进：加容器 / 升档 / 降档

框架是**可以长的**，但长法有纪律。三种动作都**不改历史**：

| 动作 | 什么时候 | 步骤 |
|---|---|---|
| **加容器** | 尽调后才发现需要某个可选容器；或项目长出了新的一类东西 | ① 先写该容器的 `README.md`（**放什么 / 什么时候进 / 什么时候出 / 不在这里放什么**）→ ② 加进 `项目清单/README.md` 的**结构视图**与 `<GOV_ROOT>/README.md` 的容器一览 → ③ 在当轮记录里写明「**为什么加**」与触发信号 → ④ 登记一条 **`DEV`**（类型＝口径/结构），不要静默加 |
| **升档** | 命中 `tier-selection.md` §六 的任一升档信号 | ① 对照 §二 表格列出**本档缺哪些容器 / 序列 / 仪式步骤** → ② **逐个补**，用同一套模板（不要发明新格式）→ ③ 改 `<GOV_ROOT>/README.md` 的「档位」节 + 补「为什么不选更高档」的理由 → ④ 门槛类规则（标记为「必选 · 标准档起」的那些）此时才生效 |
| **降档** | 命中降档信号（连续 10 轮无 `ISS`/`DEV`、容器长期空转、单人自问自答） | ① **不删任何文件** → ② 在该容器 `README.md` 写一行「**本容器 `<日期>` 起暂停使用 —— 原因：`<…>`。历史记录保留，不再新增。**」→ ③ 改档位节 → ④ 登记一条 `DEV`（说明为什么降） |

**三条禁令**（否则演进会演变成腐化）：

1. **降档不删文件** —— 历史记录不可恢复，删掉它等于抹掉「当时到底发生了什么」。
2. **升档不跳步** —— 不能"直接从轻量跳到重型"，中间档的容器与仪式必须补齐；跳过的那一档会在第一次出事时暴露。
3. **演进动作本身要留痕** —— 加/升/降都是**结构变化**，必须进当轮记录与 `DEV`。**只改文件不记录 = 下一个会话不知道框架曾经变过。**

**判据**：演进完成后，`项目清单/README.md` 的结构视图、`<GOV_ROOT>/README.md` 的容器一览、以及实际目录树**三者必须一致** —— 不一致就是演进做了一半。
