# 授权状态机：登记 → 派发 → 执行

> 这套框架里**最独特、也最容易做错**的部分。
> 它约束的不是「做什么」，而是**「谁有权让什么发生」**。

---

## 一、三段授权，互不推定 【必选】

| 段 | 含义 | 产出 | 授权了什么 |
|---|---|---|---|
| **登记** | 把一件事记进队列 | `计划队列/NNN-<slug>.md` | **只授权「记住它」** |
| **派发** | 把它提升为「本轮要做」 | 文件**移入**活跃计划目录并改名 `YYYY-MM-DD-NNN-<slug>.md`，追加「派发补充」节 | **只授权「可以开工」** |
| **执行** | 动手改代码 | 真正的改动 + 记录 | **这才是动代码的授权** |

### 铁律

> **没有派发件，「执行」这条指令不授权任何代码改动。**

即使队列项写得再详细、用户说「开始吧」，只要**没有派发件**，就不构成动代码的授权。
用户的原话若要直接动代码，走 §三 的「同轮直授」旁路（那是合法路径），
**但那条路要求逐字留痕 + 登记偏差** —— 旁路不是无痕的近路。

**为什么这么严？** 因为这三段历史上真的被混过：
有人看到队列里有条详细记录，就以为「既然写得这么清楚，直接做吧」——
而那条记录可能**因为可写范围、前置条件、或用户还没拍板**，本来就**不该做**。
「写得详细」与「批准执行」是两件事，混淆它们不会当场出错，而是**在第三轮才炸**。

---

## 二、派发的动作细节 【必选】

派发 = **移动**（不是复制）文件 + **改名** + **追加一节**：

```
计划队列/007-fix-thing.md
  → 活跃计划/2026-10-16-007-fix-thing.md
     （追加「派发补充（2026-10-16）」节）
```

**为什么必须移动而不是复制**：复制会产生两个副本，随后必然出现
「哪份是权威」的争论，并最终导致**两份不同步的真相**。
这和整个框架反复出现的「不留双份记录」是同一条纪律。

### 「派发补充」节必填栏

```markdown
## 派发补充（YYYY-MM-DD）

- 本轮范围：
- 本轮轮次号：
- 执行顺序：
- **执行期第 1 步＝复核本件全部引用**（行号/路径/接口名逐条实测）。
  **为什么**：计划件写就之后，仓库仍在被并行的编辑推着走 ——
  **普通 `file:line` 会在轮内老化**。实测过：一份派发件自曝其引用的行号**整体偏移 +14**
  （内容全对、行号全偏）。
- 落点可达性核验（若本件写死 UI 落点，必须给证据）：
- 执行期硬停（挑本轮真实会撞到的，逐条写明触发条件）：
- 隔离声明（触及侧 / 已知交织文件）：
- 越界预案：
- 收尾处置：
```

---

## 三、同轮直授（合法旁路） 【必选】

用户当轮原话点名一个**具体**改动时，可以不做派发件直接执行。条件三条：

1. 逐字记录原话（进「拍板落档」节）；
2. 写明「同轮直授、未走派发」；
3. **登记一条偏差**（类型 = 口径/留痕）。

**不得事后补造派发文件** —— 那等于伪造流程时序。时序的价值全在「它当时真的是这样发生的」。

---

## 四、「拍板落档」节 【必选】

任何**已定稿的决策**（用户原话 + 依据）都进这里，执行时**无需再拍**。

```markdown
## 拍板落档

- YYYY-MM-DD 用户原话：「<逐字>」
  → 落定：<具体决定>
- YYYY-MM-DD 用户原话：「<逐字>」
  → 落定：<具体决定>
```

**为什么逐字**：概括会丢掉限定条件。历史上出现过「用户说 A 场景可以，执行者概括成『可以』，
到 B 场景也照着做」的事故。**原话是唯一能事后复查的东西。**

---

## 五、可写范围检查（登记时就要做） 【必选】

队列项模板里有一条**必填栏**：

```
- 可写范围：
    ✅ 全部触点在「可写圈」内 → 默认可执行
    ⛔ 有触点在圈外 → 需当轮特别授权（逐个列出圈外的文件/目录）
    — 不涉代码（纯文档 / 用户决策）
```

**登记时判定，不要等到派发时** —— 否则会出现「排了半天队，派发时发现整条做不了」。

---

## 六、硬停：什么情况下停下等用户发话 【必选】

硬停不是「谨慎行事」，而是**明确的、必须等用户当轮原话才能继续的动作**。
尽调阶段要与用户一起确定这个清单，并写进宪法。**常见形态**：

- **图形界面启动**（需要人看着才能验的东西）
- **修改运行时数据目录**（用户真实数据，不在仓库内）
- **依赖与打包配置变更**
- **任何 git 写操作**（在无 VCS 的项目里则是「物理删除任何东西」）
- **真实凭据 / 真实外部服务调用**
- **物理删除资产、文档或日志**
- **覆盖不可恢复的快照**
- **未拍板的设计问题**
- **集成任何未文档化的上游面**（铁律 2）

写法要具体到**触发条件**，不是一句「重大改动要问」。例如：

> ✅ 「在无 git 的工作副本里，任何会**减少文件总数**的操作」
> ❌ 「重大删除需要确认」

---

## 七、越界处置 【必选】

**越界即硬停**：

1. 停下。
2. 报告**该任务为什么在可写范围内做不成**（具体到文件）。
3. 等用户原话。

**不得**：

- 为了让门禁变绿而「临时」改根配置、社区包、或工具脚本；
- 改门禁阈值来绕过检查；
- 把越界动作拆小到「看起来不算越界」。
