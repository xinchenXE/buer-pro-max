# 门禁与硬停

> **门禁**回答「做完了吗」，**硬停**回答「现在能不能动手」。
> 两者的共同要求：**清单具体到可执行，且不许有空行。**

---

## 一、门禁表 【必选】

### 怎么填

**只填尽调探到的真命令。** 探不到的写 `不适用 + 原因：<原因>`。
**空行是有害的** —— 事后无法区分「查过，本仓库没有这一项」与「根本没查」。

### 通用表结构（按项目裁剪）

| # | 门禁 | 命令 | 通过判据 | 日志落点 |
|---|---|---|---|---|
| 1 | 类型检查 | `<项目真实命令>` | exit 0 | `<缓存目录>/<slug>-typecheck.log` |
| 2 | 单元测试 | `<项目真实命令>` | `Tests N passed` | `...-test.log` |
| 3 | 构建 | `<项目真实命令>` | exit 0 | `...-build.log` |
| 4 | 静态审计 | `<项目真实命令>` | 关键词 / 阈值 | `...-audit.log` |
| 5 | 全量闸门 | `<项目真实命令>` | exit 0 | `...-check.log` |
| 6 | **文档基线同步** | `<元门禁，见下>` | 基线数字与判据一致 | `...-docsync.log` |
| 7 | **引用完整性** | `<元门禁，见下>` | `dead=0` | `...-refcheck.log` |
| 8 | 视觉/交互走查 | `<走查命令>` | N 景 M PASS / `verdict: PENDING_HUMAN_REVIEW` | `...-walk.log` + 证据文件 |
| — | 格式 | **不适用 + 原因**：`<原因>` | — | — |

### 两道**语言无关的元门禁**（强烈建议任何项目都上）

这两道不依赖任何语言，且**恰好覆盖本框架最容易失效的两处**：

#### 6. 文档基线同步

扫描**受治理的文件分类计数**（源码 / 测试 / 脚本 / 工具），与写在规则文档里的基线数字比对。

- **新增或删除文件时，必须在同一轮改判据。**
- **为什么需要它**：这份框架的索引里写着「文件作用清单」，而清单会静默腐化 ——
  加了文件没更新清单，清单就开始说谎，且**没有任何一道别的门禁能发现**。

实现要点：把基线数字写在**一处**（脚本里的常量或一个 sidecar 文件），
规则文档引用它，不要两边各写一份。

#### 7. 引用完整性（死链门）

扫描治理文档里的**路径引用与文档间链接**，报告不存在的目标。

- 常见形态：Markdown 链接、`path/to/file:line` 形式的引用。
- **两类扫描面**：`live`（活文档，错误即红）与 `frozen`（冻结历史面，错误只报告不拦）。
  **冻结面里允许有历史遗留的死链** —— 它们是账本的一部分，**不要去"修好"它们**。
- **关键陷阱**：**任何「报告某路径已死」的文档，本身会被当成新的死链**。
  必须提供**抑制标记**（如 `<!-- ref-check:off -->` … `<!-- ref-check:on -->` 包裹块，
  或行末 `<!-- noref -->`），并**打印被抑制的条数**——否则抑制标记会变成藏污纳垢的地方。
- **不得为了让门变绿而加豁免行**；当轮修好自己的引用。

> **实测教训**：一轮里同一个「报告死链反被计为死链」的坑**连续踩了三次**。

### 门禁的三条总纪律

1. **判定一律以退出码为准**，不看输出里的自然语言。
   （Windows/PowerShell 下：管道退出码不可信，一律 `*>` 重定向到日志文件再判 `$LASTEXITCODE`。）
2. **环境性失败必须记录并归因**，不得粉饰、不得跳过。
3. **不得为了让门变绿而放宽门禁**（改阈值、加豁免、跳过）。

---

## 二、新增门禁的顺序纪律 【必选】

> **先定标准，再加门。** 倒过来会让门变成「为过门而调标准」的工具。

实测教训：某道审计门**只解析颜色 token，全文 0 处检查字号** ——
于是「全 PASS」与「一批 9–11px 的小字」可以同时成立，用户报「字看着模糊」时才被发现。

**正确顺序**：① 用**性质**而非**名单**定义判据 → ② 验证判据有牙齿（临时造一个违规，确认它变红）
→ ③ 接到门禁里。

**判据要用性质，不要用类名表**：

> ✅ 「无字距设置的类必须 ≥11px」（新增的小字正文自动被拦）
> ❌ 「以下 42 个类名必须 ≥11px」（新增的类不在名单里，永远拦不住）

## 三、硬停清单 【必选】

**尽调阶段与用户一起确定，写进宪法。** 写具体触发条件，不写「重大改动」。

```markdown
**硬停（需用户当轮原话）：**
- 图形界面启动（<具体命令>）
- <项目特有的危险操作>
- 修改运行时数据目录 `<路径>`
- 依赖与打包配置变更
- 真实凭据 / 真实外部服务调用
- 物理删除资产、文档、日志
- 覆盖任何已有快照
- git 写操作（无 VCS 时：「任何减少文件总数的操作」）
- 未拍板的设计问题
- 集成任何未在《接口文档》里登记的外部面
```

### 「不需要用户发话」的一侧也要写

**默认可做**的清单同样重要 —— 否则执行者会对每件小事都停下来问，
治理成本压垮治理收益。

**常见合理默认**：改本体源码、跑门禁、写文档与记录、打只增不覆盖的快照、
在缓存目录里跑一次性脚本。

---

## 四、禁止操作清单 【必选】（内容按实际脚本扫描，可能很短）

尽调时**从实际的脚本与配置里扫出来**，不要凭想象列。

扫什么：

- 脚本里的递归删除、`rm -rf`、清理逻辑的**目标路径参数**；
- 会写**仓库之外**的命令（安装器、系统级写）；
- 覆盖目录/文件的构建步骤；
- CI 的**触发条件**（通常明确写着「不得修改」）；
- 打补丁机制（改它会导致 lockfile 哈希变 → 需要额外授权）。

写法：

```markdown
## 禁止操作

1. **`<脚本路径>`** —— <它做的危险动作>（`file:line`）。
   <什么时候它可以被运行 + 需要什么条件>。
2. ...
N. **递归删除指向仓库路径，以及任何绕过沙箱策略的删除**。
```

---

## 五、与完成宣告的关系 【必选】

门禁全绿是**完成宣告的前提**，不是完成宣告本身。
（见 `completion-ritual.md`：门禁通过 ≠ 闭环仪式走完。）

> **常见误解**：「门全绿了所以做完了」。
> 门禁只证明**代码没问题**，不证明**计划文档、索引、清单、记录都同步了**。
> 而后者恰恰是这套框架存在的理由 —— 代码是给人用的，记录是给**下一个会话**用的。
