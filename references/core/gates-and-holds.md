# 门禁与硬停

> **门禁**回答「做完了吗」，**硬停**回答「现在能不能动手」。
> 两者的共同要求：**清单具体到可执行，且不许有空行。**

---

## 一、门禁表 【必选】

### 怎么填

**只填尽调探到的真命令。** 探不到的写 `不适用 + 原因：<原因>`。
**空行是有害的** —— 事后无法区分「查过，本仓库没有这一项」与「根本没查」。

> **填表期的「不适用」与运行期的「不可判定」是两件事，不要混。**
> 前者 = 本仓库根本没有这一项；后者 = 命令存在，但**这次**跑不出可信结果
> （超时 / 无权限 / 依赖缺失 / 上游截断 / 解析失败）。
> 把「不可判定」记成 PASS 或 FAIL 都会误导下一轮：它既不是「过了」，也不是「东西坏了」。

### 通用表结构（按项目裁剪）

| # | 门禁 | 命令 | 通过判据 | **探测不可得时** | **红了的自愈出口** | 日志落点 |
|---|---|---|---|---|---|---|
| 1 | 类型检查 | `<项目真实命令>` | exit 0 | 超时 / 依赖缺失 → `UNDECIDABLE` + 原因 | 手工：按报错行修复 | `<缓存目录>/<slug>-typecheck.log` |
| 2 | 单元测试 | `<项目真实命令>` | `Tests N passed` | 命令不可执行 → `UNDECIDABLE` | 手工：按失败用例修复 | `...-test.log` |
| 3 | 构建 | `<项目真实命令>` | exit 0 | 同上 | 手工 | `...-build.log` |
| 4 | 静态审计 | `<项目真实命令>` | 关键词 / 阈值 | 解析不出结果 → `UNDECIDABLE` | 机修：`<项目真实的 --fix 命令>`，**先修后验** | `...-audit.log` |
| 5 | 全量闸门 | `<项目真实命令>` | exit 0 | 同上 | 手工 | `...-check.log` |
| 6 | **文档基线同步** | `<元门禁，见下>` | 基线数字与判据一致 | 取数被截断 → `UNDECIDABLE`（见本节「门禁的五个面」②） | 机修：重算并回填基线（**与检测同源**） | `...-docsync.log` |
| 7 | **引用完整性** | `<元门禁，见下>` | `dead=0` | 扫描面为空 → `UNDECIDABLE`（0 个受检 ≠ 0 个坏的） | 手工：当轮修好自己的引用 | `...-refcheck.log` |
| 8 | 视觉/交互走查 | `<走查命令>` | N 景 M PASS / `verdict: PENDING_HUMAN_REVIEW` | 无显示环境 → `UNDECIDABLE`，**不得当 PASS** | **报告级**（不阻断）或 人工 + 用户原话确认 | `...-walk.log` + 证据文件 |
| — | 格式 | **不适用 + 原因**：`<原因>` | — | — | — | — |

**自愈出口三选一（不允许留空）：**

1. **机修** —— 写出能真正修复该门的命令。它必须与检测器**同源**
   （同一份 pattern / 常量），带 `--dry-run`，**归属有歧义时只报告不改写**。
   机修一律**先于校验**执行（`修 → 验`），不要反过来。
2. **手工** —— 写明「谁、按什么步骤」。「再跑一次」不算步骤。
3. **报告级** —— **不得挂阻断**。恒红又无修复路径的检查项只能待在这里。

> **一句话判据**：随便挑一行，问「它红了，下一个动作是什么？」
> 答不出来、或答案是「再跑一次」—— 这一行就没填完。
>
> **为什么不许留空**：一个恒红的阻断门 = 治理体系的空转开关。
> 整轮「应用失败 → 回滚 → 空转」之后，没人知道下一步该改哪里。

### 两道**语言无关的元门禁**（强烈建议任何项目都上）

这两道不依赖任何语言，且**恰好覆盖本框架最容易失效的两处**：

#### 6. 文档基线同步

扫描**受治理的文件分类计数**（源码 / 测试 / 脚本 / 工具），与写在规则文档里的基线数字比对。

- **新增或删除文件时，必须在同一轮改判据。**
- **为什么需要它**：这份框架的索引里写着「文件作用清单」，而清单会静默腐化 ——
  加了文件没更新清单，清单就开始说谎，且**没有任何一道别的门禁能发现**。

实现要点：把基线数字写在**一处**（脚本里的常量或一个 sidecar 文件），
规则文档引用它，不要两边各写一份。

#### 7. 引用完整性（死链门）

扫描治理文档里的**路径引用与文档间链接**，报告不存在的目标。

- 常见形态：Markdown 链接、`path/to/file:line` 形式的引用。
- **两类扫描面**：`live`（活文档，错误即红）与 `frozen`（冻结历史面，错误只报告不拦）。
  **冻结面里允许有历史遗留的死链** —— 它们是账本的一部分，**不要去"修好"它们**。
- **关键陷阱**：**任何「报告某路径已死」的文档，本身会被当成新的死链**。
  必须提供**抑制标记**（如 `<!-- ref-check:off -->` … `<!-- ref-check:on -->` 包裹块，
  或行末 `<!-- noref -->`），并**打印被抑制的条数**——否则抑制标记会变成藏污纳垢的地方。
- **不得为了让门变绿而加豁免行**；当轮修好自己的引用。

> **实测教训**：一轮里同一个「报告死链反被计为死链」的坑**连续踩了三次**。

### 门禁的四条总纪律

1. **判定一律以退出码为准**，不看输出里的自然语言。
   （Windows/PowerShell 下：管道退出码不可信，一律 `*>` 重定向到日志文件再判 `$LASTEXITCODE`。）
2. **环境性失败必须记录并归因**，不得粉饰、不得跳过。
3. **不得为了让门变绿而放宽门禁**（改阈值、加豁免、跳过）。
4. **探测不可得 ≠ 通过**：命令存在、但这次跑不出可信结果 →
   记 `UNDECIDABLE` 并显式播报，**不得记 PASS，也不得记 FAIL**。
   它与填表期的「不适用 + 原因」不是一回事（见本节开头）。

> **为什么第 4 条是独立的**：把「取不到真值」当 `0` 消费，会判出**方向相反**的结论 ——
> 于是「修复建议」把本来正确的文档改错。这比没有门禁更难发现。
> **处置只需一个词 + 一条播报义务**；不要把它升级成状态机。

### 门禁的五个面（新增或复审任何一道门时逐条回答）

前面「新增门禁的顺序纪律」（§二）回答**怎么造一道门**；这五问回答**怎么知道这道门没瞎**。

| # | 面 | 要回答的问题 | 对应已踩过的坑 |
|---|---|---|---|
| ① | **判据面** | 用**性质**还是**名单**？判据本身会不会静默跳过？ | #26 |
| ② | **取数面** | 数据源有上限 / 分页 / 窗口吗？「**末条从哪来**」？终止判据是什么？ | #27 |
| ③ | **语料面** | 被它保护的文档在不在语料里？会不会自己证明自己？ | #21 |
| ④ | **覆盖自证** | 怎么证明「**查了 N 个**」而不是「N 个都好」？0 个受检对象时报什么？ | #26 防 2 |
| ⑤ | **结果与出口** | `PASS` / `FAIL` / `UNDECIDABLE` 各记什么？红了之后**谁、按什么步骤**修？ | 本节表格两列 |

> **五问里最容易被跳过的是 ②**：判据没写错，但**喂给判据的输入被上游截断**。
> 症状是「对已经修好的输入持续报错」，看起来像判据坏了，其实输入不全。
> 凡是消费分页 / 限流 / 窗口 API 的门，必须回答「本页满了之后还有没有下一条」；
> 终止判据只能是「**本页不满**」——「本页为空」会截断「满页后仍有第 N+1 条」的形态。

### 档位裁剪：这三件事不是每档都同等填

门禁表本身是【必选】，但上面的新列**按档位承担**，避免给轻量档造空规则
（「空规则会稀释真规则的约束力」）。

| 档位 | 探测不可得 | 自愈出口 | 取数面 / 五问 |
|---|---|---|---|
| **微型** | 不生成治理根，不涉及 | 不涉及 | 不涉及 |
| **轻量** | 表里写一句「探测失败记不可判定 + 原因」 | 写一句「**手工都写不出步骤的门**才降报告级；有手工出口的仍可阻断」 | 仅当门依赖外部数据源时回答「末条从哪来」 |
| **标准** | **逐行**填「探测不可得时」 | **阻断级门必须逐行填出口** | 依赖外部数据的门回答全部五问 |
| **完整 / 重型** | 同标准 | 同标准；机修门标「修 → 验」顺序 | 同标准，并在轮次记录里留覆盖自证 |

**微型档**的正确处置仍是「不装」——不要为了这张表给单文件脚本建治理根。

## 二、新增门禁的顺序纪律 【必选】

> **先定标准，再加门。** 倒过来会让门变成「为过门而调标准」的工具。

实测教训：某道审计门**只解析颜色 token，全文 0 处检查字号** ——
于是「全 PASS」与「一批 9–11px 的小字」可以同时成立，用户报「字看着模糊」时才被发现。

**正确顺序**：⓪ 确认**取数面完备**（数据源有上限吗 / 怎么知道读到末条 / 终止判据是什么）
→ ① 用**性质**而非**名单**定义判据 → ② 设计**三值结果**（不可判定记什么）
→ ③ 定义**自愈出口**（没有就降为报告级，不挂阻断）→ ④ 验证判据有牙齿
（临时造一个违规，确认它变红）→ ⑤ 接到门禁里。

> ⓪ 是后加的：**判据写对了、输入被上游截断**，门一样会瞎（见 §一「门禁的五个面」②）。
> 先确认取数面，再谈判据，避免「为过门而调标准」发生在错误的语料上。

**判据要用性质，不要用类名表**：

> ✅ 「无字距设置的类必须 ≥11px」（新增的小字正文自动被拦）
> ❌ 「以下 42 个类名必须 ≥11px」（新增的类不在名单里，永远拦不住）

## 三、硬停清单 【必选】

**尽调阶段与用户一起确定，写进宪法。** 写具体触发条件，不写「重大改动」。

```markdown
**硬停（需用户当轮原话）：**
- 图形界面启动（<具体命令>）
- <项目特有的危险操作>
- 修改运行时数据目录 `<路径>`
- 依赖与打包配置变更
- 真实凭据 / 真实外部服务调用
- 物理删除资产、文档、日志
- 覆盖任何已有快照
- git 写操作（无 VCS 时：「任何减少文件总数的操作」）
- 未拍板的设计问题
- 集成任何未在《接口文档》里登记的外部面
```

### 「不需要用户发话」的一侧也要写

**默认可做**的清单同样重要 —— 否则执行者会对每件小事都停下来问，
治理成本压垮治理收益。

**常见合理默认**：改本体源码、跑门禁、写文档与记录、打只增不覆盖的快照、
在缓存目录里跑一次性脚本。

## 三·补、破坏性操作的回读义务 【必选】

任何**不可逆 / 破坏性**动作（移动、归档、删除、改名、批量替换、覆盖快照）执行后，
必须用**独立于执行手段**的方式回读对象真值，并同时确认两件事：

1. **目标对象已按预期改变**；
2. **非目标对象未被改变**。

第 2 条才是抓得到「参数被静默忽略」的那一条 —— 快捷命令隐式取号、
`exit 0` 但参数没生效，这类事故里目标看起来「改了」，只有反向核对能发现改错了对象。
**这是纪律，不是铁律** —— 它不改变体系归属，但不做会直接丢数据。

> 判据：回读的命令**不能是**执行时用的那条。用 `grep` 改的，就用 `git diff` 回读；
> 用脚本改的，就用 `ls` / `git status` 回读。

## 四、禁止操作清单 【必选】（内容按实际脚本扫描，可能很短）

尽调时**从实际的脚本与配置里扫出来**，不要凭想象列。

扫什么：

- 脚本里的递归删除、`rm -rf`、清理逻辑的**目标路径参数**；
- 会写**仓库之外**的命令（安装器、系统级写）；
- 覆盖目录/文件的构建步骤；
- CI 的**触发条件**（通常明确写着「不得修改」）；
- 打补丁机制（改它会导致 lockfile 哈希变 → 需要额外授权）。

写法：

```markdown
## 禁止操作

1. **`<脚本路径>`** —— <它做的危险动作>（`file:line`）。
   <什么时候它可以被运行 + 需要什么条件>。
2. ...
N. **递归删除指向仓库路径，以及任何绕过沙箱策略的删除**。
```

## 五、与完成宣告的关系 【必选】

门禁全绿是**完成宣告的前提**，不是完成宣告本身。
（见 `completion-ritual.md`：门禁通过 ≠ 闭环仪式走完。）

> **常见误解**：「门全绿了所以做完了」。
> 门禁只证明**代码没问题**，不证明**计划文档、索引、清单、记录都同步了**。
> 而后者恰恰是这套框架存在的理由 —— 代码是给人用的，记录是给**下一个会话**用的。
