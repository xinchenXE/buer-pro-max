# 铁律（不可违背）

> 铁律是这套框架的**下限**：它们不是「最好这样」，而是「违背了就不算这个体系」。
>
> **档位选哪些铁律，只看下面这张表 —— 这是全库唯一的权威。**
> **不要用「N 条铁律」这种计数表述**：条数会随触发条件变，写死必然漂。
>
> | 档位 | 生效的铁律（**按 ID**） | 附带 |
> |---|---|---|
> | 微型 | 无 | 不装治理 |
> | 轻量 | ③ | +「核心约束」1 / 2 / 4（见 `mandatory-vs-optional.md` §2.1） |
> | 标准 | ③ ④ ⑤ ⑥ | −「①②（若触发则加）」 |
> | 完整 | ③ ④ ⑤ ⑥ + ①②（按触发） | 全部 |
> | 重型 | 同完整 | + 角色与权限矩阵（`tier-selection.md` §五） |
>
> **读法**：`③` = 本文件第 3 条。**①② 是「必选 · 触发」** —— 有外部上游或只读边界才启用，
> 无边界时用它们的**形态**（= `mandatory-vs-optional.md` §2.2 #20 的两层可写范围），
> 而不是整条跳过。
>
> **为什么用 ID 不用条数**：轻量档只启用了 §「核心约束」里的三条，其中两条**不是铁律**
> —— 它们是核心约束 #2 与 `anti-patterns.md` 的 #1。把它们都叫「铁律」会让读者
> 去本文件里找，然后找不到。
>
> **条数与编号不得引入歧义**：新增规则一律**追加**为增补节，不插进列表中间。
> 原因：全仓（含历史计划、既有文档）大量按「铁律 2」「铁律 6」这样的**编号**引用，
> 插入一条会让既有引用集体错位。这条本身就是一个一般规律：**凡是被编号引用的东西，只能追加**。

---

## 1. 零上游改动 【可选 · 触发：有外部上游 / 只读边界】

**上游子树（submodule / vendored 目录 / 被整体替换的依赖）只读，任何功能分支不得编辑其内文件。**

配套纪律：**上游 pin 的更新与产品行为的改动必须分开提交**。混在一个提交里，
事后无法回答「这次行为变化是上游带来的还是我们带来的」——而这恰恰是排期决策的唯一依据。

```
判据：<upstream-path>/ 内的文件指纹与其 pin 记录一致；不一致即红。
```

**通用化说明**：若项目没有外部上游，本条**不启用**，并在宪法里写明原因。
不要为一条不存在的边界写一条空规则——空规则会稀释真规则的约束力。

---

## 2. 只经公开面集成 【可选 · 触发：有外部上游 / 只读边界】

**只允许通过已文档化的公开面与上游交互**：契约接口、事件、插件/扩展点、样式变量、路由。
**禁止**读取上游的内部存储格式、依赖未文档化的字段、或对上游内部结构做假设。

```
判据：本次改动引用的每一个上游符号，都能在《上游/外部接口文档》里找到对应条目。
找不到 = 硬停，先补文档或改道，不得「先用着」。
```

### 这条铁律要拆成两层（通用化的关键）

原形态「零上游改动 + 只经公开面集成」预设了「有上游」。
**通用化后拆成两层，两层都保留，只是「上游是谁」由尽调填**：

| 层 | 通用表述 | 无上游时的退化 |
|---|---|---|
| **内层（边界）** | 本仓库某个子树**只读**，不得编辑 | 项目内也会有只读区：生成物、第三方、冻结的配置 |
| **外层（接口）** | 只能经**已文档化**的公开面跨过这条边界 | 跨模块/跨包调用只能走对外导出的面，不许伸手进内部 |

**没有上游的项目仍然有这条线**：`dist/`、`node_modules/`、lockfile、代码生成产物、
第三方 SDK 的封装层——它们都是「只读 + 只经公开面」。这条铁律的价值在于
**迫使「边界」被显式写下来**，而不是在于边界之外一定是别人。

### 教训：文档判断「能不能集成」，不判断「有没有」

> 曾经的错误：因为《接口文档》里没有某接口，就得出「没有任何公开面能拿回一段结构化文本」。
> **错。** 实测该接口存在且可用。

**正确姿势**：

- 文档用来判 **「能不能集成」**（铁律 2 的判据）—— 文档里没有 = 不许用。
- 判 **「有没有」** 时去读上游的**契约源码**（`packages/**/src/api/*.ts` 之类）——
  文档是**索引**，不是**世界本身**。

反向的错也一样常见：**把「文档里有」当成「可用」**。
两个方向同源——都是**把文档当成了世界**。

## 3. 门禁全绿才算完成 【必选】

每一轮改动必须通过**全部门禁**才能宣告完成。

- 门禁清单与命令见 `gates-and-holds.md`，**每个项目的门禁不一样，由尽调填**。
- **不得为了让门禁变绿而放宽门禁**（改阈值、加豁免、跳过检查）。
  门禁变红的正确处置是：修好，或者**如实记录为环境性失败并归因**。
- 环境性失败必须记录并归因，**不得粉饰**。

> 这条铁律真正防的是**「为了让检查通过而修改检查」**——它比任何一次具体缺陷都更接近体系的失效。

---

## 4. headless 安全 【必选】

**构建、类型检查、单元测试、以及各类 smoke 测试不得依赖图形界面启动。**

理由不是洁癖：一旦门禁需要人肉开图形界面，它就**不可能在无人值守下跑**，
于是要么被跳过、要么被「我本地跑过了」替代——两者都让门禁名存实亡。

需要图形界面的验证走**证据容器**（截图/走查记录），并作为**独立的一步**，
由用户当轮发话才执行。

---

## 5. 未落地的东西不得声明为已落地 【必选】

（原形态：两个尚未落地的模块 `<module-a>/` 与 `<module-b>/` 在运行时落地前保持私有文档脚手架，
不得声明可加载入口。）

**通用表述**：**任何尚未实现的部分，不得暴露看起来可用的入口。**
文档脚手架就是文档脚手架，不得声明为包入口、插件入口、可加载模块、可注册服务。

配套：**每次改动都要重新确认这条仍然成立**——一个「暂时没接线」的入口很容易在后续轮次里
被误当成已有能力。

## 6. 凡可能有问题的地方一律和用户讲清楚 【必选 · 触发：有用户可见面】

> **本条的「形态」是必选的，「落地方式」是条件化的。**
> 只要有**用户可能因不知道而做错**的地方，就必须告知 —— 这一条无例外。
> 但**"告知落在哪"取决于项目有没有 UI**：有 UI 落进界面文案；无 UI 落进 CLI 输出、
> 库的异常消息、日志或 README。**下面「附带的可执行细则」中带 🖥 的，只在有 UI 时适用。**

**风险、边界与限额的具体数值、推荐做法、以及不这么做的后果，必须出现在用户看得见的文案里。**

适用面**不限于设置页**：控件、错误行、降级态、确认门、悬停明细、空态、走查存证，同此纪律。

四条必须说清：

1. **会发生什么**
2. **边界/限额的具体数值**（不是「较大」「可能很慢」，是具体数）
3. **推荐怎么做**
4. **不这么做会怎样**

**只写进计划文档不算告知。** 必须落到**用户实际会看到的那个面**并渲染出来：
**有 UI** → 界面文案（本地化字典）；**无 UI** → CLI 输出 / 异常消息 / 日志 / README。

### 附带的可执行细则

> 🖥 = **仅当项目有用户可见界面时适用**；纯库 / CLI / 后端服务按等价的非 UI 落点执行。

- **数值取运行时权威面**：限额/配额/默认值优先读运行时投影或 schema 默认值，**显示实际生效值**；
  确需写死时在注释里标出处与失效条件。
- 🖥 **灰态三件套**：不可用的控件不许只置灰 —— **置灰 + 原因 + 出路**，三者齐备。
  （**无 UI 的等价**：不可用的能力在报错里说清「为什么不可用 + 出路」。）
- 🖥 **有损与不可逆操作事前告知**：走二次确认浮层，框内列出「这么做会怎样 / 不那么做会怎样 /
  推荐哪种 / 具体数值对比」。
  （**无 UI 的等价**：`--force` / `--yes` 类开关必须有明确的 dry-run 或确认提示，并在帮助文本里写明后果。）
- **外发与隐私明示**：任何会离开本机的内容（路径、文件名、内联正文、凭据引用名）
  必须在首次使用告知或常驻提示里说明去向；密钥明文永不回显。
- **失败指名对象与原因**：错误提示必须说清**哪个**文件/路由/字段失败，上游原文 message
  **原样透出**（不概括、不吞）；批量操作按**条目粒度**反馈。
- **能力边界诚实**：拿不到的预检不许假装能防 → 改为**常驻轻提示 + 失败时解释**。

### 门禁挂钩

> **新增用户可见提示 → 文案齐备并落单测断言。**（有 UI：本地化字典双语言；
> 无 UI：断言该错误分支产生含关键信息的输出。）
> **只写实现不写告知视为任务未完成。**

### 为什么本条是「必选 · 触发」

**它的失败模式是「任务未完成」**：实现而不告知 = 该任务没做完，必须补做 —— 那就是返工。

**它确实贵**（每条用户可见文案要文案齐备 + 单测；有损/不可逆操作要二次确认），
**但贵不是降为可选的判据**。这套框架的判据只有一个：**不做会不会返工**。

**可伸缩的是两件事**：
1. **告知面的大小** —— 项目越小、用户越少，需要告知的**面**就越小（可能只有一条错误提示）；
2. **告知的落地形态** —— 有 UI 落界面，无 UI 落 CLI/异常/日志/README。

但**「要不要告知」不是可伸缩项**：只要存在**用户可能因不知道而做错**的地方，那处就得告知。

**唯一整条不适用的情形**：**完全没有使用者**（既无终端用户，也无其他开发者调用的内部模块）——
此时 `/dev/null` 式的内部纯计算，没有"用户看得见的面"可言。**这是触发条件，不是省略理由。**

## 冲突裁决：目标项目的规则 vs 本框架的铁律

> **为什么要有这一节**：端到端试跑实测遇到 —— 目标项目的 `AGENTS.md` 写着「不需要执行构建，用户会自己做」，
> 而本框架铁律③ 要求「门禁全绿才算完成」。两者直接矛盾，而当时**没有任何成文机制**告诉生成者怎么办。

**裁决顺序**（从高到低）：

1. **用户当轮原话点名 > 一切**。
2. **目标项目**自己写下的**明确禁令** > 本框架的**默认门禁表**。
   但必须同时做三件事，缺一不可：
   - 在门禁表里**显式写**「不适用 + 原因：<引用那条项目规则的文件与行号>」；
   - 在宪法段的铁律后缀上一句「**本项目口径：…**」；
   - **登记一条留痕**（`DEV` 序列或队列总表的注记区）。
3. **本框架的铁律 1–6 > 本框架的其他文件**。
4. **同级文件冲突 → 以 `工作范式.md` 为准**（宪法段是它的绑定摘要，不是竞争者）。

**三条禁令**：

1. **不得静默跳过**。不能因为「项目禁止」就把门禁表该行**删掉** ——
   删了下一个会话就分不清「不需要」与「忘了写」。写「不适用 + 原因」。
2. **不得拿「项目规则」当万能钥匙**。只有**明确写下**的禁令才能覆盖默认门禁；
   项目没写过的事，不能推测「他们大概不想这样」。
3. **不得双向适用**。项目的禁令只影响**那一项门禁**，不影响本框架的其他规则。

**判据**：问自己「这个门为什么不跑？」能答出**具体文件与行号**。答不出来 = 超范围。
