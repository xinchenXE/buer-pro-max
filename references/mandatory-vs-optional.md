# 规则的必选与可选

> **本 skill 的目的：尽最大可能降低返工概率，一次性做对。**
>
> **判定标准由此确定**：问一句 ——
> **「这条不写，会不会导致返工？」**
>
> - **会**（任何项目、任何档位都可能撞上）→ **【必选】**
> - **只在主题物存在时才可能**（有 UI 才有落点、有上游才有边界）→ **【可选 · 触发：X】**
> - **什么都不会发生**（只是解释为什么）→ **【参考】**
>
> ⚠ **注意「可选」的判据是「主题物可能不存在」，不是「项目小所以用不上」。**
> 一套轻量项目的文档照样会有计数、照样会引用行号、照样会做批量替换 ——
> **那些纪律在任何规模下都防返工，因此是必选。**
>
> 装多了确实会稀释约束力，但那指的是**不适用于这个项目的规则**；
> **不是「这条做起来麻烦」。**

---

## 一、标记约定

> **标记只回答一个问题：「要不要写进生成件？」**
> 它**不回答**「写多长」「写多细」—— 那是各规则文件自己的事。

| 标记 | 含义 | 处理 |
|---|---|---|
| **【必选】** | 不写就会返工 —— 与项目规模、技术栈无关 | 任何档位、任何项目都写进生成件 |
| **【必选 · 触发：X】** | **有 X 这个主题物时是必选**；X 不存在则整条不适用 | 尽调时判 X；不成立就**不写**，并记明原因 |
| **【必选 · 标准档起】** | **档位门槛**：达到该档才必选 | 按尽调判出的档位取 |
| **【可选 · 触发：X】** | 只有 **X 这个主题物存在**时才适用 | 尽调时判 X；不成立就**不写**，并记明原因 |
| **【可选 · 推荐】** | 有益，但**要不要由用户定** | **初始化前说明「为什么推荐 + 成本影响」→ 用户同意就做，不同意就跳过**（见 §六） |
| **【参考】** | 不是规则，是**说明 / 历史 / 教训** | 读，但不落进宪法 |

> **「必选 · 触发」与「可选 · 触发」的区别只有一条**：
> 主题物**存在**时，前者**必须写**，后者**可以写**。
> 两者都**不该在主题物不存在时出现** —— 写一条空规则会让人习惯性忽视整张表。

### 2.2 跨会话与文档纪律（**不写必然返工**）

| # | 项 | 不写会怎样 |
|---|---|---|
| 5 | **默认阅读顺序** | 下一个会话重新发现上下文 → 重复劳动、或重做已决定的事 |
| 6 | **静默跳过 = 漏做** | 「查过没有变化」与「根本没查」不可区分 → 台账开始说谎 |
| 7 | **权威落点 vs 世界本身** | 判「有没有」查错地方 → 得出**完全相反**的结论（实测踩过两次） |
| 8 | **规则载体的多处同步** | 漏改的那处**看起来更权威** → 下次会话按旧规则执行，且自认合规 |
| 9 | **计数漂移** | 数字开始说谎，且**没有任何门禁能发现**；静默更正则同型漂移会重演 |
| 10 | **行号会漂** | 引用失效 → 按错的行号改代码 → 改错地方（实测整体偏 +14） |
| 11 | **替换前断言唯一命中** | 「什么都没改却报告成功」—— 最危险的失败模式，且不会被发现 |
| 12 | **跨轮操作的留痕** | 非计划内的动作无记录 → 「这是谁删的」永久不可考 |
| 13 | **重复标题 = 文件被复制** | 文档被整份复制而**没有任何门禁能抓**，且**复制反而让死链门更绿** |
| 14 | **主题不竞争** | 两份同类活跃计划 → 各执一词、两份都不权威 |
| 15 | **走查证据链** | 不做 → **假绿**：「看起来验过了，其实没验」是返工最贵的形态。含 **`verdict` 不得自证**、**条数逐条核对**。<br>**「可见≠可点」部分触发：有 UI** —— 有 UI 时**必须做命中测试** |
| 16 | **headless 安全**（**触发：有构建/测试门禁**） | 门禁需要人肉开图形界面 → 它就不可能无人值守跑，于是**要么被跳过、要么被「我本地跑过了」替代** |
| 17 | **未落地不得声明为已落地**（**触发：有未落地脚手架**） | 未实现的入口被当成已有能力 → 后续依赖它的工作全部白做 |
| 18 | **落点可达性核验**（**触发：有 UI**） | 落点写死了但被别的东西盖住/藏起 → **功能做了却不可达**，且只有真机才能发现 |
| 19 | **告知纪律**（**触发：有用户可见面**） | 实现而不告知 = **该任务未完成**；用户因不知道而做错 → 返工。可伸缩的是**告知面的大小与落地形态**，不是「要不要告知」 |

### 2.3 边界与安全（**两层形态在任何项目都成立**）

| # | 项 | 不写会怎样 |
|---|---|---|
| 20 | **可写范围：两层形态**（内层＝某子树只读；外层＝只经公开面跨过） | 边界不明 → 改了不该改的，或**不敢改该改的**（后者同样是返工）。<br>即使无上游，`dist/`、lockfile、生成物、第三方封装层仍是这条线 |
| 21 | **禁止操作清单** | 误跑一次不可逆操作 = 返工的最大来源。<br>内容按实际脚本扫描，**可以很短，但不能没有** |
| 22 | **新增门禁的顺序纪律**（先定标准再加门） | 倒过来会让门变成「为过门而调标准」的工具 → 阈值被悄悄放宽 |
| 23 | **清理/验证的完备性** | 只验一部分 → 残留物活过完成宣告（实测：探针在打包树里留了好几轮） |
| 24 | **下结论前必查**（别把「脚本没做」当「产品不行」） | 错误结论 → 整轮工作白做 |

### 2.4 必选里的**唯一例外**

**铁律 1·2（零上游改动 / 只经公开面集成）的「乙类部分」是可选的** ——
因为**外部上游这个主题物可能不存在**。

但**它们的形态（= #20 的两层边界）是必选的**。区别只在措辞：

| 情况 | 写法 |
|---|---|
| 有外部上游 | 「`<上游路径>` 只读；只经《接口文档》登记的面集成」 |
| 无外部上游 | 「`<生成物/第三方目录>` 只读，只由工具链写；不得手工编辑生成文件」 |

**两者是同一条纪律的两个实例。** 无上游的项目**不是不需要这条**，
而是它的「只读边界」画在别处。

## 五、落地方式（生成时怎么做）

1. **必选集（§二）** → 无条件写进宪法段与 `工作范式.md`。
   **不因项目小、档位低而省略。**
2. **可选集（§三）** → 尽调时判**主题物是否存在**：
   - 存在 → 写进生成件。
   - 不存在 → **不写**，并在 `<GOV_ROOT>/README.md` 记一行：
     `未纳入的可选规则：<哪些>，原因：<主题物不存在 + 尽调证据>`。
3. **推荐（§六）** → **初始化前逐项说明理由，用户定**；同意的写、跳过的记一行。
4. **参考（§四）** → 不落进生成件。

> **第 2 步的「记一行」是必须的** —— 否则下一个会话读到本 skill 后，
> 会以为那些规则是**遗漏**，然后"好心"把它们全加回来。
> **写明"为什么没要"与"要什么"同等重要。**

## 六、**推荐**项的处理流程

「推荐」是**第三类** —— 它既不是必选（不写不必然返工），也不是主题物触发（它与主题物无关）。
**判据是「性价比」**：做它要花一点成本，但它能省掉的排查消耗更大。

### 说明格式（**三段必填，缺一不可**）

**每一项推荐，在说给用户听时，必须把下面三段讲全。** 缺任何一段，
用户都**无法做出知情选择** —— 那这条推荐就退化成了「我建议做」，等于没说。

| 段 | 必答什么 | 反面例子（不许这么写） |
|---|---|---|
| **① 为什么推荐** | 它**防的是什么** —— 具体到「会怎么返工 / 会花多久排查」 | ❌「这是好实践」→ 空洞，用户无法判断 |
| **② 成本影响** | 做它**要花什么** —— 一次性成本多少、**长期每轮**多少、要不要额外实测或引入新工具 | ❌「成本很低」→ 不给数，「低」是相对的 |
| **③ 不做的后果** | 跳过它**具体会怎样** —— 多数是「可以，但下次遇到同样的事要重新查一遍」 | ❌「会有风险」→ 什么风险？多大？ |

> **三段都要落到「可比较的量」上**：时间（分钟/小时）、每轮频率、文件数、是否有额外依赖。
> 讲不出量，就说明你自己还没想清楚这条推荐值不值。

### 处理流程（四步）

1. **识别**：尽调阶段列出本次命中的全部「推荐」项。
2. **说明**：**在执行初始化之前**，按上面的**三段格式**逐项讲给用户。
3. **用户定**：同意 → 写进生成件；不同意 → **跳过，不写**。
4. **记录**：同意的与跳过的**都记一行**在 `<GOV_ROOT>/README.md`：
   `推荐项：<做了什么>｜<跳过了什么，原因：用户选择>`。

> **第 2 步必须在初始化之前**，不能生成完再问。
> 生成后问 = 用户面对既成事实做选择，那时「跳过」的代价是删文件，而不是不生成。

### 当前已知的「推荐」项

| 项 | ① 为什么推荐（防什么） | ② 成本影响 | ③ 不做的后果 | 落在哪 |
|---|---|---|---|---|
| **环境事实一节**<br>（本机实测的坑） | 下一个会话**一模一样地重踩**同一个坑，且**踩的时候不知道在重复** | **一次性**：每个项目必须现场实测，不能套用别人的（这正是它不通用、因此不是必选的原因）。<br>**长期**：几乎为零 —— 只在踩到新坑时追加一行 | 可以，但下次遇到同样的事要**重新查一遍**；这类坑单次排查常以**小时**计 | `工作范式.md` §六；`anti-patterns.md` #17 |
| **会话交接件**<br>（`session-handoff.md`） | 跨会话丢四件事：上一轮改了什么 / 现在卡在哪 / 下一步做什么 / **别踩哪些坑**。其中第四件最贵 —— 不写就**永久丢失** | **一次性**：建一个 `登记提示词/` 目录 + 一份模板。<br>**长期**：**每轮收尾多写一份文件**（约 20–40 行），加进闭环仪式 | 下一个会话要**自己重新发现上下文**（读一堆文档 + 猜）；上一轮踩过的坑有较大概率被重踩 | `登记提示词/`；闭环仪式第 8 件 |

> **这两项为什么不是必选**
>
> - **环境事实**：事实**逐项目不同**，无法从本 skill 预设 —— 新项目要自己踩、自己记。
> - **交接件**：**只有跨会话才需要**。单会话能做完一件的项目，它的成本（每轮一份文件）
>   大于收益；那类项目在索引里维护一个「下一步」小节就够。
>
> **它们为什么还值得每次都问一句**：代价都是**几行到几十行字**，
> 收益都是**省掉一整轮重新发现**。**性价比悬殊** —— 但值不值，由用户按自己的会话节奏定。

**读法**：
- **`③` 与 `#3` 同号是巧合** —— 一个是铁律编号，一个是必选集编号。**不要跨表按号引用。**
- 引用时**带上表名**：写 `铁律 ③` 或 `必选 #16`，不要只写「第 16 条」。
- 本表是**唯一载体**。其他地方提「某铁律对应某个必选条目」时**指向本表**，不各写一份。

> **为什么要有这张表**：实测发现同一件事在不同文件里被标成 `#2/#7`（anti-patterns 编号）
> 又被标成 `#15/#18`（必选集编号），读者无法判断是不是同一件。本表消除了这个歧义。

> **关于「铁律为什么没有必选条目」**：六条铁律的**形态**都必选（见 §2.2 #15），
> 但每条铁律的**具体实例**都依赖一个主题物 ——
> 那条铁律约束的边界真实存在时，它才是一条能被执行、能被检查的规则。
> **边界不存在时写一条空规则，会让人习惯性地忽视整张铁律表。**
