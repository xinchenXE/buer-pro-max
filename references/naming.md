# 产物命名（中 / 英）

> **本文件回答一个问题：生成的 `<GOV_ROOT>/` 里，目录和文件叫什么名字？**
>
> 结论先说：**默认中文，可切换英文；两套命名一一对应，语义完全相同。**

---

## 一、为什么要问这个

这个 skill 的产物是一棵**给人读的文档树**。名字用中文还是英文，会同时影响三件事：

| 影响 | 中文命名 | 英文命名 |
|---|---|---|
| **可读性**（中文团队） | ✅ 一眼看懂「活跃计划 / 归档计划」 | ❌ 要先查对照 |
| **可移植性** | ⚠️ zip/tar/git 在跨语区、macOS NFD 归一化下有风险 | ✅ 纯 ASCII，零风险 |
| **与代码仓库的一致性** | ⚠️ 仓库里通常是英文目录 | ✅ 一致 |
| **搜索/补全** | ⚠️ 输入法切换 | ✅ 直接敲 |

**没有绝对正确** —— 所以由用户在**初始化之前**选一次，然后**整棵树按选定的那套生成**。

---

## 二、什么时候问

**尽调 §1.2 的第 5 问**（`SKILL.md` §一 与 `references/due-diligence.md` §二 同步）：

> **「治理文档的目录和文件名，用中文还是英文？」**
>
> - 默认**中文**（若用户没意见）
> - 若目标仓库的要求是跨语区 / 需要提交进英文仓库 / 有 CI 处理路径 →
>   建议**英文**
> - **一旦选定，整棵树只用那一套，不要混用**

---

### 3.3 模板文件（**这两套是给生成者看的，不进目标项目**）

`templates/` 与 `_xxx模板.md` 的命名**保持不变**（它们只在维护这个 skill 时用）。
生成时按上面的对照表落到目标项目里。

### 3.4 编号与 slug（**两套通用，不翻译**）

| 形态 | 例子 | 说明 |
|---|---|---|
| 队列项 | `NNN-<slug>.md` | slug 用小写 ASCII + 连字符 |
| 实施计划 | `<日期>-<轮次号>-<slug>.md` | 日期 `YYYY-MM-DD` |
| 问题 | `ISS-NNN-<slug>.md` | |
| 偏差 | `DEV-NNN-<slug>.md` | |
| 快照 | `snap-<日期>-<label>.manifest.tsv` 等 | |
| 轮次号 | `R01` | |

**slug 永远 ASCII** —— 中文只出现在**标题与摘要**里，不出现在文件名里
（这一条**两套命名都适用**，理由是可移植性与命令行的可操作性）。

## 四、选完之后必须做的事

1. **在 `<GOV_ROOT>/README.md` 的「档位」一节记一行**：
   `命名方案：<中文/英文>（<日期> 用户选择）`。
2. **把选定的名字写进 `项目清单/README.md` 的结构视图** —— 结构视图是唯一的目录真源。
3. **不要混用**：不要出现「`活跃计划/` 里放 `queue-register.md`」这种混搭。
   一旦用户反悔要换命名 → 走**演进模式**（`SKILL.md` §四）：整批改名 + 修全部引用 +
   登记一条 `DEV`，**不要逐个文件慢慢改**（那会长期处于半中文半英文状态）。

---

## 五、为什么不把它做成"两套模板"

**成本**：23 份模板 × 2 套 = 46 份，且每次改规则要改两遍 ——
这正是 `doc-sync-discipline.md` §一 明令避免的「规则载体多处同步」。

**替代做法**：**模板只有一套（中文命名）**，另加这张对照表。
生成时按用户的选择**一次性映射**。

> **这是「拆两层」的又一次应用**：模板的**形态**只有一套，
> 「叫什么名字」由这张表在生成时填。
