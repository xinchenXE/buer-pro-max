## 一、可选容器：由用户选，默认值挂档位

下面五个容器**不是每档都生成**。它们各自解决一类问题，**问题不存在的项目不该有它们** ——
一个长期空置的容器会开始收留不该放的东西。

**判定顺序**：① 按档位取**默认生成集** → ② 尽调中发现触发信号则**改判** →
③ **在生成前把结论告诉用户一句，让他能推翻** → ④ **绝不生成"以防万一"的容器**。

| 容器 | 解决什么 | 触发信号（尽调时看这个） | 默认生成集 |
|---|---|---|---|
| **`证据/`** | 人工/视觉验证的证据往哪放 | 有任何「需要人看才能判断对不对」的东西（UI / 渲染 / 交互 / 音频 / 验收材料） | 标准档起生成；轻量/微型不生成 |
| **`缓存/`** | 生成物不落仓库根 | 门禁/走查会产生日志，或已出现「原文件名不改」的引用需求 | 标准档起生成；轻量视需要 |
| **`工具/`** | 自制门禁脚本的住处与契约集中处 | 项目**没有**现成的门禁脚本位置：查三项 —— ① 无 `scripts/` 目录、② 无 `Makefile` / `package.json` 的 `scripts` 条目、③ 无 CI workflow。**三者同时成立才算触发**；任一存在即视为「已有位置」，不因本条生成（可在门禁表里指向原位） | 完整档起生成；轻量/标准可指向原位 |
| **`快照/`** | 无 VCS 时的唯一退路 | **跑 `git rev-parse --show-toplevel`：失败 = 无 VCS；成功但治理根不在该仓库内 = 治理记录不受 git 保护**。两种情形都必须生成并进宪法硬停清单 | **条件是「VCS 覆盖不到治理根」**，与档位无关 |
| **`标记删除/`** | 破坏性删除的可逆中间态 | **没有自动触发信号 —— 由用户选**。生成前必须把「启用 / 不启用」的优缺点与建议一次说全（见下） | 无档位门槛；**默认建议与 `快照/` 同源启用** |

### 三条纪律

1. **默认值是建议，不是判定**。档位给默认，**用户随时可以推翻** ——
   所以要**先说结论再生成**（「标准档默认带 `证据/` 与 `缓存/`，你要不要？」），
   **不要生成了再问**。
2. **不生成 ≠ 这件事不用管**。例如不生 `证据/`，人工验证的截图仍要**有个地方放** ——
   在尽调结论里写明「证据落 `<已有位置>`」。
   **容器可以省，纪律不能省。**
3. **每个可选容器都带自己的触发信号**（见上表）。
   判断依据是**信号**，不是「高档位就该有」—— 高档位但纯后端的项目，`证据/` 仍是多余的。

### 生成后写进 `<GOV_ROOT>/README.md`

在「容器一览」表里，未生成的容器**不写**；但要在**档位**一节记一句：

```markdown
**可选容器**：本档位默认带 <A/B>；本次**未生成** <C>，原因：<触发信号不成立>。
```

**「本次未生成 X，原因 Y」必须写** —— 否则下一次会话会以为那是遗漏，
然后"好心"把它建起来，收留一堆本该放别处的东西。

### 由用户选的容器：`标记删除/` 的必答三件事

`标记删除/` 与上表其它四个不同：**它没有自动触发信号，必须由用户选**。
生成前把下面三件事**一次说全**，让用户能推翻 —— **不要生成完再问**。

| 选项 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **A. 与 `快照/` 同源启用** | 覆盖唯一真正危险的情形：删了没有任何版本历史能还原；且快照是时点全量，本容器补的正是**逐文件**粒度 | 多一个容器 | ✅ **默认推荐** |
| **B. 所有项目默认生成** | 有 git 的项目也保护**未跟踪文件**（新建后被误删，git 同样救不回来） | 对熟练用户是噪声；治理根在 git 里时价值被稀释 | 适合大量未跟踪产物 / 多人协作 |
| **C. 不生成** | 容器最少 | 破坏性删除退回「硬停 / 真删」两态 → 执行者要么事事来问，要么自行豁免 | 仅当用户明确说不要中间态 |

**标准问法**（一次说全三段：好处 / 代价 / 建议）：

> 「检测到 **<无 VCS / 治理根不在仓库内 / 有 VCS>**。要不要生成 `标记删除/`？
> **好处**：破坏性删除变成「移进候删区」，可逐文件还原，不必每次来问你。
> **代价**：多一个容器，删文件时要多一步「移入 + 登记」。
> **我的建议**：**<启用 / 不启用>**，因为 <一句话>。」

**选了 C 也要留痕**：在尽调结论里写「破坏性删除无中间态，删除一律走硬停」——
让这个选择**显式**，而不是靠默认。

**启用时必须在别处同步四件**（漏一件就是半成品）：

1. **宪法段硬停清单**加一行：`真删 标记删除/ 内的任何文件（含清空容器）`；
2. **`工作范式.md` 增「删除纪律」节**：破坏性删除的唯一入口 = 移入本容器；可再生物豁免（含反向判据「删了能用一条命令重建吗」）；
3. **操作记录的触发项**由「删除」一种扩为四种：移入 / 还原 / 真删 / 直接删可再生物；
4. **门禁表**：文档基线与孤儿检查的扫描面**排除本容器**（它是候删件，不是活文档）。

> **只读边界不能被「移动」绕过**：来自 `apk/`、上游封装、锁文件、冻结配置的东西
> **不得移入本容器** —— 搬进来等于删掉了它们。这条要写进容器 README 的「不在这里放什么」。
