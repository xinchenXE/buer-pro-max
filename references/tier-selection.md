# 档位阶梯与项目画像

> **装多了比装少了更糟。** 多余的容器不会「以防万一」，它会**稀释真容器的权威** ——
> 当一个空目录长期存在，人就开始往里丢不该丢的东西。
>
> 本档位表是 `SKILL.md` §二 的展开。**选档依据是尽调结果，不是用户偏好。**

---

## 一、五档阶梯

| | **微型** | **轻量** | **标准** | **完整** | **重型** |
|---|---|---|---|---|---|
| **形态** | 单文件脚本 / 周末工具 / 一次性实验 | 单人小工具或库 | 单人/小团队的主力项目 | 跨会话长周期产品 | 多仓库 / 多角色 / 有发布与合规 |
| **判据** | 1–2 个源文件；无测试或只有冒烟 | < 5k 行；无外部上游；改动面 1 个目录 | 5k–50k 行；有 VCS；改动面 2–3 个目录；跨会话 | > 50k 行，或 > 20 轮历史 | 多个维护者；有发布列车；有审计/合规要求 |
| **计划容器** | 无 | 活跃 / 归档 | + 休眠 / 归档文档 | + 丢弃 = 全部五个 | 全部五个 + **按流向分子目录** |
| **ID 序列** | 无 | 队列 + 轮次 | + 问题 | + 偏差（四序列） | 四序列 + **命名空间前缀** |
| **台账** | 无 | 队列总表 | + 问题记录 / 修改记录 | + 偏差总账 / 操作记录 | + 审计台账 / 发布台账 |
| **闭环仪式** | 无（提交即闭环） | 3 步 | 5 步 | 7 步 | 7 步 + 发布门 + 双人签署 |
| **铁律**（按 ID，见 `iron-rules.md` 顶部） | 无 | ③ | ③ ④ ⑤ ⑥ | ③ ④ ⑤ ⑥ + ①②（按触发） | 同完整 + **契约化（角色矩阵）** |
| **宪法段** | 不写 | ~40 行 | ~100 行 | ~200 行 | ~200 行 + 分开的角色/权限矩阵 |
| **交接件** | 不需要 | 索引里的「下一步」小节 | **【推荐项】** | **【推荐项】** | **【推荐项】** + 按角色分发 |
| **生成动作** | **什么都不生成** | 最小集（见 §四） | 默认集（见 `SKILL.md` §三） | 全部 | 全部 + 角色矩阵 + 发布台账 |
| **可选容器** | — | `缓存/` 视需要 | `证据/` + `缓存/` | `工具/` + 前三者 | 同完整档 |

> **「推荐项」不是档位默认** —— 它走 `mandatory-vs-optional.md` §六 的三段流程，用户点头才生成。本表只说「哪些档位**可能**需要它」，不说「必须有它」。

## 二、怎么选（判定流程）

**先过规模闸，再看协作/上游/发布信号。** 顺序反了会让「单人 + 大仓库」被短路到标准档。

```
① 规模闸（按 §一 判据）
   源文件 1–2 个 且 不打算回来维护 ─────────────▶ 微型（不装）
   源文件行数 < 5k ────────────────────────────▶ 轻量
   5k–50k ────────────────────────────────────▶ 标准（候选）
   > 50k 行 或 历史轮次 > 20 ──────────────────▶ 完整（候选）
                                                    │
② 上调信号（可上不可下 —— 命中任一条就升档）        │
   有外部上游 / 版本耦合依赖 ──▶ 至少 §三选完整       │
   有第二个维护者 ────────────▶ 至少标准             │
   有发布列车 / 合规审计 / 角色分工 ──▶ 重型          ▼
                                                   取更高的一档
```

**读法**：
- **第 ① 步按规模先落一个基线档**，它决定「下限」。
- **第 ② 步只能上调，不能下调** —— 大仓库不会因为「只有我一个人」而降到标准。
- **微型 / 轻量不会在流程里被混淆**：微型有明确判据（1–2 个源文件**且**不打算维护），
  其余低于 5k 行的走轻量。
- **判不准时取更低一档**，然后在生成件里写升档信号。

**默认取低不取高。** 判不准时 → 选**更低**一档，然后在生成件里写明升档信号。

## 三、微型档：**建议什么都不装**

### 什么时候是微型

- 单文件脚本、CLI 小工具、周末实验、一次性的数据处理
- 1–2 个源文件；没有测试，或只有一次冒烟验证
- **你不打算回来维护它**，或者它做完就不再改

### 建议

**不要用这个 skill。** 装一套治理体系的成本是真实的，而且它在这个规模上
**只有坏处**：你会花时间填一份没有人读的模板，而那份模板的存在会让你
**误以为自己有治理**。

真正需要的只有一个文件：

**形态见 `templates/_NEXT模板.md`** —— 那是唯一权威版（三节：下一步 / 已决定 / 坑）。
**本文件不复制一份**，否则两份措辞会漂（`anti-patterns.md` #12「不留双份记录」）。

`git commit -m "<做了什么>"` 本身就是闭环。**这就够了。**

### 什么时候该升到轻量

- 出现**第二件**「还没做完但先放着」的事 → 需要活跃/归档的区分
- 你**开始记不住**上一次改到哪 → 需要逐轮记录
- 你**开始复制粘贴同一个 TODO 列表** → 需要唯一的真源

## 四、轻量档：**只装最小集**

### 生成什么

```
<GOV_ROOT>/
├── README.md              ← 一句：读什么、按什么顺序读
├── 工作范式.md             ← 3 条核心约束 + 门禁表 + 3 步闭环（~60 行就够）
├── 项目清单/
│   ├── README.md          ← 精简版：这个项目里有什么、哪块能写
│   └── 尽调结论.md         ← 初始化第一步的产出（生成依据）
├── 活跃计划/              ← 未完成的计划 + 一个「下一步」小节 + `项目总结.md`
├── 归档计划/              ← 已闭环（移动，非复制）
├── 计划队列/
│   ├── 队列总表.md         ← 唯一的计数真源
│   └── _队列项模板.md
```

**就这些。** 加上 `AGENTS.md` 里的 ~40 行宪法段。

> **`项目清单/` 在轻量档也要有** —— 尽调结论必须有落点。
> 没有它，`SKILL.md` §一 那条「尽调结论写进 `项目清单/尽调结论.md`」就无处可落，
> 生成者只能凭空造目录或**静默跳过**（而静默跳过 = 漏做）。

### 轻量档的三条**核心约束**

> **它们不是「铁律」** —— 这三条来自 `mandatory-vs-optional.md` §2.1 的四条核心约束
> （这里取了轻量档适用的三条），不是 `iron-rules.md` 的六条铁律。
> 轻量档**实际启用的铁律只有 ③**（门禁全绿），见 `iron-rules.md` 顶部的「档位 → 铁律 ID」表。

1. **先计划后实施** —— 未落计划文档的改动不进代码（核心约束 #2）
2. **门禁全绿才算完成** —— 门禁表只填你**真实有**的命令，通常是 `lint` + `test` + `build`（核心约束 #3）
3. **证据不自证** —— 自己说「验过了」不算，要有输出（核心约束 #4）

### 轻量档常见的三个错误

| 错 | 后果 |
|---|---|
| 装了一堆空容器「以防万一」 | 空的容器会开始收留不该放的东西 |
| 门禁表里填了不存在的命令 | 门禁名存实亡，且**没人会发现**（因为没人在跑） |
| 给每件小事都开一个队列项 | 登记成本 > 收益，你会开始绕过它 |

**判据**：如果这套东西**每周花你的时间超过 10 分钟**，它对你来说太重了 → 降档或退回微型。

### 什么时候该升到标准

- 容器里出现**第 2 份**未完成计划
- 第一次出现「**同一个问题被独立发现两次**」 → 需要问题序列
- 第一次出现「**计划被实测推翻**」 → 需要偏差序列
- 你开始需要回答「**这个问题是什么时候发现的**」

## 五、重型档：**多出来的不是文档，是三个机制**

> **关键认知**：单人项目里，这套框架解决「**跨会话失忆**」。
> 重型项目里，它解决的是「**多角色之间谁有权做什么**」。
> 两者需要的机制**不一样** —— 把完整档原样放大，只会得到一份没人读的宪法。

### 重型档必须多出的三样

#### 1. 角色与权限矩阵

单人项目里「登记 / 派发 / 拍板 / 豁免门禁」是**同一个人**，所以可以合并成一件事。
重型项目里**必须拆开写**，否则会发生「谁批准了这次改动」无法追溯。

```markdown
## 角色与权限

| 动作 | 谁可以做 | 需要谁同意 | 记录在哪 |
|---|---|---|---|
| 登记队列项 | 任何维护者 | — | 队列总表 |
| **派发**（授权开工） | <角色> | — | 派发件 |
| **拍板**（口径未定时的裁决） | <角色> | — | 拍板落档（逐字原话） |
| **豁免门禁** | <角色> | <角色> **双签** | 审计台账 + 理由 |
| **推翻已冻结的记录** | 任何人 **都不得**（唯一例外：事实性更正 + 注记） | | |
| 发布 | <角色> | <角色> 复核 | 发布台账 |

**「特别授权」在重型档里指的是：<角色> 在当轮明确点名文件/目录/改动。**
```

#### 2. 不可变台账

审计场景下，**记录一旦写入就不可修改**。要点：

- **append-only**：后来的变化写**新的一条**，不改旧的
- **带指纹**：不可逆删除记 SHA-256；关键决定记提交哈希或签署人
- **关键动作双签**：豁免门禁、跳过验证、越过冻结面 → 两个角色
- **明确谁不能改**：连项目所有者也不能改写冻结面（否则审计失效）

#### 3. 发布列车与版本纪律

「实现完成」与「发布完成」**不是一回事**，重型档必须分开记：

```markdown
## 发布纪律

- **版本号双线制**：dev 线与 release 线**独立**，一条线的构建**不消耗**另一条的号
- **未明说大版本时，只加末尾数字**；不得自行升级大版本
- **发布前置检查**：<具体的版本号格式断言>，不通过则**构建失败而非告警**
- **发布台账**：每次发布记 版本 / 日期 / 内容摘要 / 复核人 / 产物指纹
- **实现完成 ≠ 发布完成**：前者进逐轮记录，后者进发布台账
```

### 重型档要小心的三件事

| 风险 | 表现 | 对策 |
|---|---|---|
| **编号空间爆炸** | 四个全局序列横跨五个仓库、十个团队 → 谁也不记得 `DEV-142` 是什么 | **命名空间前缀**：`WEB-001` / `API-013`；每个命名空间**独立计数**，总表里**分区列出** |
| **宪法长到没人读** | 200 行 → 500 行 → 新人直接跳过 | **分层**：必读 20 行（铁律 + 授权 + 硬停）+ 分区细则（按需查）。**不要去重写它，去拆它** |
| **冻结面被顺手更新** | 「我把那个过期数字改对了」 → 审计链断掉 | 冻结面纪律列为**最高优先级**；唯一例外（事实性更正 + 注记）写进宪法并用**门禁**兜住 |

### 重型档的一个额外判断

**「完成宣告」在这档要区分两个完成：**

- **实现完成** —— 代码写完、门禁全绿、闭环仪式走完
- **发布完成** —— 通过发布前置检查、进了发布台账、产物可追溯

**很多组织只在第一层做治理，然后在第二层出事。** 如果贵组织有发布流程，
**把发布门写进宪法**，否则它会在某次赶工时被跳过。

## 六、升降档规则（**双向**）

### 升档信号（低 → 高）

满足任一条，升一档：

- 容器里出现**第 2 份**未完成计划
- 第一次「**同一份计划被两个会话同时改**」
- 第一次「**同一个问题被独立发现两次**」 → 需要**问题序列**
- 第一次「**计划被实测推翻**」 → 需要**偏差序列**
- 第一次「**有人在不知道上下文的情况下改了你改过的东西**」 → 需要**交接件**
- 第一次「**两个人同时动同一个模块**」 → 需要**角色矩阵**
- 第一次「**你回答不出『这次改动是谁批准的』**」 → 需要**签字与发布台账**

### 降档信号（高 → 低）

**降档同样重要，且大多数人不敢做。** 满足任一条，考虑降一档：

- 连续 **10 轮**没有新增 `ISS` / `DEV` → 那两个序列在**空转**
- 某个容器**连续 3 个月**只增不减地空着，或只在初始化那天有内容
- 只有**一个人**在跑，而所有「待用户裁决」都是**自问自答** → 授权矩阵是**自欺**
- **每周花在治理上的时间超过 10 分钟**，而这个项目其实很小
- 你的记录开始**互相矛盾**（说明维护成本已超过收益）

### 降档的**正确做法**

> **不是删文件。** 是在容器 README 里写一行：
> `本容器 <日期> 起暂停使用 —— 原因：<…>。历史记录保留，不再新增。`

**为什么不能删**：历史记录的价值是**不可恢复**的。删除它等于抹掉「当时到底发生了什么」，
而这恰恰是这套体系唯一不可替代的产出。
**暂停使用 ≠ 删除历史。**

### 档位可以混合（monorepo）

**多个子项目各自一档**是正常且推荐的：

```
仓库/
├── packages/core/        ← 完整档（长期演进，多人）
├── packages/cli/         ← 轻量档（小工具）
├── scripts/one-off/      ← 微型档（不装）
└── <GOV_ROOT>/      ← 共享的宪法段与总表
```

**共享什么 / 不共享什么**：

- **共享**：宪法段（铁律与授权）、队列总表（计数真源）、ID 命名空间
- **不共享**：各子项目自己的活跃/归档容器与逐轮记录

## 七、写进生成件的部分

在生成的 `<GOV_ROOT>/README.md` 里放一段：

```markdown
## 档位

**当前档位：<档>**（<日期> 判定）
**依据**：<逐条对应判据>
**为什么不选更高档**：<写明>

**升档信号**（出现任一条就升一档）：<逐条列出>
**降档信号**（出现任一条就考虑降档）：<逐条列出>

**降档的正确做法**：在容器 README 里标注「暂停使用 + 原因」，**不删历史**。
```

**「为什么不选更高档」必须写** —— 它是下一次复查时的对照基准。

**可选容器**（`证据/` / `缓存/` / `工具/` / `快照/`）另按触发信号判：
**档位给默认，用户可推翻；不生成的要写明原因。** 详见 `SKILL.md` §三·补。
