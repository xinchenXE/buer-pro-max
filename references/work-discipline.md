# 工作方法纪律（评审 / 测试先行 / 调试 / 并行 / 头脑风暴）

> **本文件回答的是「怎么做」，不是「谁有权做」。**
> 授权三段、可写范围、门禁表、完成宣告回答后者；本文件回答前者。
> 两者**正交**：有执行权，不等于知道该按什么顺序写代码。
>
> **为什么必须有这一层**：这套框架原本的门禁全是**机器门** —— 类型检查、测试、构建、
> 死链、计数。它们能证明「没坏」，**不能证明「做对了」**。
> 实测反例见 `anti-patterns.md` #35：八道门全绿，产品首屏黑屏。
>
> **生成时怎么用**：本文件是**生成者的依据**；落到项目里的形态是
> `工作范式.md` §3.10 与队列项/计划件的对应槽位（见文末「落地位置」）。
> 产物里**不得**出现本文件的路径（`SKILL.md` §3.0.2 第 5 项）。

## 一、代码评审 【必选 · 触发：有产品代码改动】

> **门禁全绿 ≠ 做对了。** 机器门没有一道读代码 —— 它们只回答「能不能跑」，
> 不回答「跑的是不是该跑的东西」。

### 什么时候必须评

命中**任意一条**即触发（R1–R5，逐条给判据，不用「重大改动」这种需要猜的说法）：

| # | 触发条件 | 判据（可核对） |
|---|---|---|
| R1 | 产品代码改动 ≥ 200 行 | `git diff --numstat` 里非文档、非生成物的行数之和 |
| R2 | 改到 ≥ 3 个公共面 | 公共面 = 对外接口 / 事件 / 扩展点 / 样式变量 / 路由；逐个列名 |
| R3 | 新增依赖或动工具链 | 依赖清单、锁文件、构建配置、CI 配置有 diff |
| R4 | **门全绿但行为不对** | 有可复现的异常现象，而所有门都退出 0（这一条**不可机械化**，由执行者声明） |
| R5 | 动可写范围的高危档 | 触及 D / F 档文件，或 `patches/**` 一类补丁面 |

**不触发时**：验证门表里写 `代码评审 | 不适用 + 原因：<无产品代码改动 / 未命中 R1–R5> | —`。
**不留空** —— 空行与「评过没问题」在事后无法区分。

### 评审三问（每问都要落到具体位置，不能只答「没问题」）

| 问 | 要回答什么 | 不合格的答法 |
|---|---|---|
| **Spec** | 这次改动**逐条**对应计划里的哪个任务？有没做的吗？有夹带的吗？ | 「基本符合计划」 |
| **质量** | 边界、失败路径、并发/时序、资源释放怎么处理？证据在哪？ | 「逻辑没问题」 |
| **可维护** | 命名、分层、重复、注释密度是否与周围代码一致？下一个人改它要多久？ | 「代码挺清晰」 |

**评审结论的落点**：`<GOV_ROOT>/证据/评审-<轮次>.md`，字段含
`verdict: PENDING_HUMAN_REVIEW` + 三问逐条 + 触发项 + 评审人。
**`verdict` 不得由执行轮自己改成 PASS**（`completion-ritual.md` §四「证据不自证」）。

### 单人项目的退路（必须写明，不能假装有第二个人）

没有第二评审人时，允许**自评**，但报告里必须：
① 显式标注 `评审人：执行者本人（自评）`；② 三问逐条给**可核对的位置**
（`file:line` / 命令输出 / 测试名），而不是形容词；③ 触发 R4 时**必须**补一条
可复现的验证命令，且真的跑一次。

**自评是降级，不是等价。** 写成自评比假装成复核诚实。

### 收到评审反馈时的纪律

- **技术严谨优先于配合**：先验证反馈是否成立，成立就改，不成立就说清为什么不成立。
- **禁止表演式认同**：「好问题」「您说得对」但代码没动，是比不回复更坏的反馈。
- **不确定先验证**：对「可能是 X 引起的」这类反馈，先复现再下结论（见 §三）。

## 二、测试先行（TDD） 【必选 · 触发：有可自动化测试的产品代码】

> **先写会红的测试，并真的跑一次看到它失败。** 没红过的测试不知道在测什么 ——
> 它可能从来没被执行过，也可能断言的是别的东西。

### 时序（不按这个顺序做的，不叫 TDD）

1. **RED** —— 写一个**当前实现会失败**的测试，**跑一次**，确认失败信息符合预期。
   **没跑出红的测试 = 还没有 RED**。
2. **GREEN** —— 写**最少**的实现让它变绿，不做测试没要求的事。
3. **REFACTOR** —— 在测试保持绿的前提下清理结构；每改一步重跑。

### 判据

- 新增纯函数 / 组件 / 分支 → 有对应测试，且**第一次运行的结果被记录**（红 → 绿）。
- Bug 修复 → 先写一个**复现该 bug 的失败测试**，再修；修完该测试转绿且**旧测试不红**。
- 重构 → 重构前后测试集合相同且全绿。

### 明确不适用（写了「不适用 + 原因」，不要留空）

| 情况 | 为什么 | 替代 |
|---|---|---|
| 纯文档 / 配置 / 治理树改动 | 没有可断言的运行行为 | 走门禁 + 回读核对 |
| 一次性脚本、探测命令 | 不打算回来维护 | 跑一次并留输出证据 |
| 项目没有测试框架且引入成本高于本次收益 | 工具链不存在 | 在计划里写明，并给出**手工可复现**的验证命令 |
| 纯样式微调（不改变结构） | 断言价值低于视觉走查 | 走查证据 + 命中测试（`completion-ritual.md` §四） |

> **「不适用」是结论，不是默认。** 每次都要回答「为什么这里不需要」，
> 而不是「这次比较急」。

## 三、系统化调试 【必选 · 触发：出现缺陷或异常行为】

> **未复现之前不得提出修复。** 猜出来的修复即使让现象消失，也没有人知道它修的是什么。

### 四步，顺序不能跳

1. **复现** —— 给出**确定性**的复现命令 / 步骤 / 输入。不能稳定复现时，
   先记录观察到的条件（频率、环境、数据形态），**不得**直接进入第 3 步。
2. **隔离** —— 用**最小改动集**缩小范围（二分、注释、替换为桩、单变量开关）。
   每步都要留「改了什么、现象变没变」。
3. **假设（必须可证伪）** —— 写成「如果是 X，那么 Y 会发生」的形式；
   不能写成「可能是缓存问题」这种无法判定的句子。
4. **验证（只改一个变量）** —— 一次只动一个变量，跑**能区分假设真假**的那条命令；
   结论与现象都要记录。

### 纪律

- **修复必须能解释原现象**：说不出「为什么原来会错」，就还没找到根因。
- **修复后重跑复现步骤**：确认原现象消失，且**非目标行为未变**。
- **不要顺手修**：调试中发现的其他问题登记进问题记录，不夹带进本轮。
- **探针要清理**：调试用的日志/开关，收尾时删干净，并留一条「已清理」的核对
  （`anti-patterns.md` #4 的完备性核验同理）。

## 四、并行执行与隔离 【必选 · 触发：并行会话 / 子代理 / 多路同时改】

> **「隔离」＝写集不重叠 + 每轮快照 diff，不是 `git worktree`。**
> 本框架不假设提交模型；worktree 只是某些宿主上的**可选**手段，不是纪律要求。
> **禁止**把「开了 worktree」当成「已经隔离」—— 写集重叠时，合并仍然冲突。

### 并行提示词必须写清三件事（P1–P3）

| # | 字段 | 写什么 | 不写的后果 |
|---|---|---|---|
| **P1** | **写集** | 本路**允许修改**的文件/目录，逐个列出 | 两路同时改同一文件 → 后合并者覆盖前者，且**无人察觉** |
| **P2** | **阅集** | 本路**只读**的文件；以及**已知交织**的文件（别人可能同时在改） | 基于过期阅读下结论，行号与内容在轮内老化 |
| **P3** | **合并顺序** | 谁先合、谁基于谁、冲突时以谁为准 | 合并顺序变成随机，重放时结果不同 |

**判据**：并行提示词里这三项**各自可 grep 到**；缺一项 = 该路不具备并行条件，
改为串行或先拆分任务。

### 合并前的最小核对

- 两路**写集交集为空**；不为空时必须写明交集文件的**合并顺序**与**冲突裁决人**。
- 每轮结束打一次**快照 / diff**（有 VCS 用 `git diff --stat`，无 VCS 用快照），
  逐文件对照写集：**目标已改**且**非目标未改**（`gates-and-holds.md` 的回读义务）。
- 发现越界写入 → **停下来报告**，不要「顺手对齐」。

## 五、头脑风暴 【可选 · 推荐】

> **默认关闭。** 它不是默认工作流的一部分，只在**写计划时**由用户决定是否开启。

### 五条硬规则

1. **唯一入口**：只有**写计划时**询问一次「本轮是否需要开启头脑风暴」。
   实施中、收尾时、调试时都**不得**自行发起。
2. **必须给建议与理由**：不能只问「要不要」。给出「建议开 / 建议不开」+ 一句为什么，
   让用户能直接拍板。
3. **默认关闭**：用户没表态 = 不开。
4. **用户拍板后才开**：问完就自己开始，等于自授权。
5. **用途受限**：只用于**更准确地找出或分析问题**；不用于产出实施步骤、不用于替代计划。

### 三段说明（初始化时按本框架的推荐项格式讲清楚）

| 段 | 内容 |
|---|---|
| ① 为什么推荐 | 口径未定时直接开工，容易整轮返工；先用一轮把问题问准，能省掉一轮实施 |
| ② 成本影响 | 每轮写计划时多一次询问（约半分钟）；真开启时多一轮对话 |
| ③ 不做的后果 | 不是不能做，而是「问题没问准就开工」的风险由用户自己承担；复杂问题上通常以返工收场 |

**用户跳过时**：在 `<GOV_ROOT>/README.md` 记一行 `推荐项：头脑风暴询问位｜跳过`。
**不要把「跳过」写成「已完成」**。

## 六、与外部流程技能包共存 【参考】

> 宿主上可能装了别的流程技能包（规划 / 评审 / TDD / 调试）。**它们不是敌人，
> 但也不能直接替换本框架的授权与留痕。**

- **只借用判定标准，不借用审批流程**：可以用它的清单来问「评了没有」，
  但「谁批准了这次改动」仍以本框架的派发件与拍板落档为准。
- **接入前先声明冲突**：两边对同一件事给了不同顺序（例如先评审还是先归档）时，
  **在项目规则里写清以谁为准**，不要靠会话时的临场判断。
- **不把外部包的配置表抄进本仓库**：那张表绑定具体版本与安装环境，
  升级后会静默失效，且没有任何门能发现。要记就记**原则**，不记条目。
- **不得据此改动用户级安装**：启用 / 停用外部技能是用户的决定，不是框架的一部分。
