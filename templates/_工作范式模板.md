# 工作范式模板 → `<GOV_ROOT>/工作范式.md` 【必选】

> **这是整套体系里最重要的生成物。** 它是**规则的权威载体** ——
> 铁律、容器分类规则、实施纪律、门禁、完成宣告全在这里，其他文档都指向它。
>
> 生成树里点了这个文件，但**光有宪法段不够**：宪法是摘要（**被 `CLAUDE.md` 导入时**才会自动加载），
> 这份是**全文**（要查细则时读的）。两者的关系必须在两边都写明。
>
> **长度**：轻量 ≈60 行 / 标准 ≈250 行 / 完整 ≈500 行 / 重型 同完整。
> 下面 `## 三` 之后的「实施纪律」各节**必须按目标项目重写** —— 不要照抄 `§3.x` 的示例标题。

---

## 模板

```markdown
# <项目名> · 开发范式

> 生效：<日期>（<轮次号> 起所有改动遵循本范式）
> 适用范围：<可写范围> 与本治理体系
> 基准：<宪法段文件> 的宪法段 + <接口文档路径>
> **本文件是规则的权威载体**；<宪法段文件> 的宪法段是它的**绑定摘要**，冲突以权威载体为准。
>
> **变更记录纪律**：本文件**只增补、不静默改写**。任何改写必须在头部追加一条变更记录
> （日期 + 改了什么 + 依据 + 用户原话若有）。历史条目**不删不改**。

## 一、铁律（不可违背）

<按档位写铁律；逐条给「判据」，不只给态度。>

1. …
2. …

> **条数与编号不得引入歧义**：新增规则一律**追加**为增补节，不插进列表中间 ——
> 全仓大量按「铁律 2」这样的编号引用，插入一条会让既有引用集体错位。

## 二、计划文档范式

<按项目的容器分类规则写：完整的判定规则 + 五个容器各自的进/出条件。不要只列目录名。>

**分类规则（不可搞错）**：
- 未完成 → `活跃计划/`
- 已完成（宣告闭环）→ `归档计划/`
- 用户明确暂缓 → `休眠计划/`
- 用户明确否决 → `丢弃计划/`
- 被更新取代的原文 → `归档文档/`（原样存档、一字不改）

- **命名规范**：<阶段计划 / 修复轮计划 / 其他，按项目定>
- **每份计划必含**：背景（含证据出处）、任务分解（编号 + 验收标准）、
  偏差记录位、验证记录位
- **先计划后实施**：未落计划文档的改动不进代码；实施中发现的出入以「偏差记录」追加，
  不得静默改道
- **禁止同主题并存两份活跃计划**

## 三、实施纪律

> **下面各节是本项目的实施纪律**，按本项目的真实分层组织。
> 每一节都要给**判据**而不只是态度；用不上的节直接删掉，不留空节。
> 例外：**铁律**与**门禁**的「不适用」必须留字（它们是全集的一部分）。

### 3.1 <分层/模块组织>
<例：纯逻辑与视图分离、跨组件状态怎么传、依赖方向、禁止的跨层引用。都要给判据。>

### 3.2 <数据与状态面>
<例：谁能写、谁能读、只读镜像优先于复制写面、序列化约束。>

### 3.3 <样式/资产纪律>
<例：覆盖走 specificity 不用 `!important`、层级序固定、单次注入、类×规则不变式。>

### 3.4 <文案与本地化>
<例：哪个语言是 key 集真理源、另一语言逐键对齐、上游字符串不可改只能视觉接管。>

### 3.5 <浮层/交互返回纪律>
<例：三返回路径（✕ / 遮罩点击 / Esc）、Esc 只退最上一层、关闭清瞬态。**给出单测落点。**>

### 3.6 用户告知纪律

<写「四件必须说清的事」+ 执行细则 + 门禁挂钩；权威口径见工作范式 §一 的告知纪律。>

### 3.7 生成物与缓存纪律

**一切生成物落 `<GOV_ROOT>/缓存/`，不得写仓库根**（门禁日志 / 一次性脚本 / diff）。
**缓存可以被清理，但清理前先确认没有计划文档按裸文件名引用它。**
（本项目若无 `缓存/`，把生成物落到构建产物目录，并在此写明位置。）

### 3.8 代码可写范围

<写本项目的可写范围：用户原话（逐字）+ 甲乙丙分类表 + 按档位的默认可写清单。
本节与 <宪法段文件> 宪法段的「可写范围」节必须一致；冲突以本文件为准。

### 3.9 删除纪律　**（仅启用了 `标记删除/` 时写此节）**

**可写圈内破坏性删除的唯一入口 = 移动进 `<GOV_ROOT>/标记删除/`。**
移动**不需要用户原话**（可逆、不减少文件总数），但必须：`登记.md` 五项 + 操作记录 +
回读 + 引用核对。**真删**（删除或清空该容器内的文件）**需用户当轮原话** —— 这是硬停。

**可再生物豁免**：缓存性质的文件（门禁日志、一次性脚本、构建产物、`__pycache__`、
diff/patch/bak）**不构成破坏性删除**，直接删，只记操作记录。
**反向判据**：删掉之后能用**一条命令**重建吗？能 → 直接删；不能 → 必须移入 `标记删除/`。

**只读边界不能被「移动」绕过**：来自上游封装、锁文件、冻结配置、只读资产目录的东西
**不得移入**本容器 —— 搬进来等于删掉了它们。

### 3.10 工作方法纪律（评审 / 测试先行 / 调试 / 并行 / 头脑风暴）

> **编号**：本模板里它是最后一个固定小节。目标项目若已占用 §3.10，
> **顺延为下一个可用的小节号**（追加，不改既有编号 —— 全仓按节号引用会集体错位）。

> **门禁全绿 ≠ 做对了。** 本节的规则回答「按什么顺序做」，
> 而 §四 的门禁只回答「做完没有坏」。**有产品代码改动时，本节不得整体删除**；
> 无产品代码的项目（纯文档 / 纯配置）删掉 3.10.1–3.10.3，并在此留一行原因。

#### 3.10.1 代码评审　**（触发：R1–R5 任一命中）**

R1 产品代码改动 ≥ 200 行 · R2 改到 ≥ 3 个公共面 · R3 新增依赖或动工具链 ·
R4 **门全绿但行为不对** · R5 触及 D/F 档或补丁面。

评审三问，每问落到 `file:line` / 命令输出 / 测试名，不写形容词：
**Spec**（逐条对应计划的哪个任务、有没有夹带）· **质量**（边界、失败路径、资源释放）·
**可维护**（命名、分层、重复、与周围代码的密度一致）。
报告落 `证据/评审-<轮次>.md`，`verdict: PENDING_HUMAN_REVIEW`，
**执行轮不得自己改成 PASS**。没有第二评审人时允许自评，但必须标注「自评」，
并给可核对的位置。

#### 3.10.2 测试先行　**（触发：有可自动化测试的产品代码）**

**RED → GREEN → REFACTOR**：先写一个**会失败**的测试并**真的跑一次看到它红**；
再写最少实现变绿；最后在保持绿的前提下重构。
Bug 修复先写复现该 bug 的失败测试。**不适用时在验证门表写「不适用 + 原因」**。

#### 3.10.3 系统化调试　**（触发：出现缺陷或异常行为）**

**复现 → 隔离 → 假设（可证伪）→ 验证（只改一个变量）**。
**未复现之前不得提出修复**；修复必须能解释原现象；调试探针收尾必须清理并留核对。

#### 3.10.4 并行执行与隔离　**（触发：并行会话 / 子代理 / 多路同时改）**

并行提示词必须写清三项，缺一项即不具备并行条件：
**P1 写集**（允许修改的文件，逐个列）· **P2 阅集**（只读与已知交织文件）·
**P3 合并顺序**（谁先合、冲突以谁为准）。
**「隔离」＝写集不重叠 + 每轮快照 diff**，不是 `git worktree`；
不得用「开了隔离工作区」代替写集核对。

#### 3.10.5 头脑风暴　**（默认关闭；唯一入口＝写计划时询问）**

1. 只有**写计划时**询问一次，实施 / 收尾 / 调试中**不得**自行发起。
2. **必须给出建议与理由**，不能只问「要不要」。
3. 用户没表态 = **不开**。
4. **用户拍板后才开** —— 问完就自己开始等于自授权。
5. **用途受限**：只用于更准确地找出或分析问题，不用于产出实施步骤、不替代计划。

## 四、验证门禁（每轮必须全绿）

| # | 门禁 | 命令 |
|---|---|---|
| 1 | <门禁名> | `<真实命令>` |
| — | <不适用项> | **不适用 + 原因**：<原因> |

> 这张表是**速查**，完整的门禁表另有四列：**通过判据 / 探测不可得时 / 红了的自愈出口 / 日志落点**。
> 标准档起还应有一行 **状态机一致性**（`status-check`，契约见 skill 的 `tool-contracts.md` §七）——
> 没有这门时写「待实现 + 重建入口」，不要留空、也不要写一个不存在的命令。
> 轻量档只需记住两句：**探测失败记「不可判定 + 原因」，不得记绿**；
> **机器修不了、手工也写不出步骤的门才降报告级**（不挂阻断）；有手工出口的仍可阻断。

**补充纪律**：
- 新增纯函数/组件 → 同步新增或扩展测试（时序见 `§3.10.2`：先红后绿）
- 视觉/人工验证以证据存证；无法验证时**在轮次文档记录原因**
- 环境性失败需记录并归因，**不得粉饰**
- **不得为了让门禁变绿而放宽门禁**
- **门分两类**：**工具门**（判定＝退出码）与**评审门**（判定＝评审报告 + 用户确认）。
  两类都写进上面这张表，但**评审门不得写成一条命令**，
  也不得把「命令退出 0」当成评审通过 —— 那正是「门全绿但做错了」的来源。
```

## 写法纪律

1. **「变更记录」必须在头部**，**只增补不静默改写** —— 这条纪律本身要写在文件里，
   否则第三次改动时就会有人直接改正文。
2. **每条规则给判据，不给态度。**
   ✅ 「判据：本次改动引用的每一个外部符号都能在《接口文档》里找到条目」
   ❌ 「应尽量使用公开接口」
3. **`§三 实施纪律` 各节标题按项目重写**，不要保留原体系的标题当占位 ——
   一个空节比没有这一节更糟。
4. **用不上的节直接删，并在删除处不留痕迹**（不要写「本节不适用」七次）。
   只有**铁律**与**门禁**的「不适用」需要留字（因为它们是全集的一部分）。
5. **本文件与宪法段的关系必须在两边都写明**，否则两处会被分别独立修改后互相矛盾。

| | <宪法段文件> 宪法段 | `工作范式.md` |

| 冲突时 | 判决 | 判决（**本文件是权威**，宪法是摘要）|

> **这一条必须与 `_宪法段模板.md` 的「冲突以 `工作范式.md` 为准」保持一致。**
> 两处方向相反时，**以本文件为准** —— 但那就意味着宪法段写错了，
> 应当**同轮改宪法段**，而不是让矛盾留着（`doc-sync-discipline.md` §一）。

**维护义务**：改任一处必须在**同一轮**改另一处。这是 `doc-sync-discipline.md` §一
说的「规则载体多处同步」在本体系内部的第一个实例 —— **它就是最容易腐化的那个。**
