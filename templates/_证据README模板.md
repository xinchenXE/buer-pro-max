# `证据/` README 模板（可选容器） 【可选 · 触发：有需人工/视觉核验的产物】

> **它回答：那些"证明这东西真的能用"的原始材料放哪。**
>
> 门禁退出码证明不了「界面是对的」。**人工/视觉验证**需要截图、录屏、审计 JSON ——
> 本容器是它们的落点，也是「**证据不自证**」这条铁律的物理载体。

---

## 模板

```markdown
# 证据 · 人工与视觉验证的原始材料

> **本目录只放原始材料，不放结论。** 结论进计划文档或轮次记录。
> 只增不改 —— 证据一旦写就不修改（改了就不再是证据）。

## 一、放什么

| 类型 | 命名 | 说明 |
|---|---|---|
| 截图 | `<类型>-<轮次>-<场景>.png` | 人工/视觉走查的产物 |
| 结构化结果 | `walk-audit-<时间戳>-<label>.json` | 见下「必填字段」 |
| 审计输出 | `<轮次>-<审计名>.json` | 对比度审计、体积审计等的完整输出 |

## 二、结构化结果文件的**必填字段**

```json
{
  "verdict": "PENDING_HUMAN_REVIEW",
  "label": "<本轮标识>",
  "items": [ { "name": "<检查项>", "status": "PASS|FAIL", "detail": "<实测值>" } ],
  "counts": { "pass": 0, "fail": 0 },
  "logPath": "<对应日志路径>"
}
```

### 三条铁律

1. **`verdict` 初始必须是 `PENDING_HUMAN_REVIEW`，且不得由执行轮自己改成 PASS。**
   执行者既生产证据、又裁决证据 —— 等于没有裁决。
2. **`counts` 必须从日志逐条核对得出，不手写。**
   实测踩过两次：记「21/21」实测 20、记「13/13」实测 14，
   根因都是**只数了关键字面、漏掉「前置断言」那一类条目**。
3. **任何验证脚本（含临时自制的）都必须产这个文件。**「自制脚本直跑」不是豁免理由。

## 三、不在这里放什么

- ❌ **结论**（「测试通过」「看起来没问题」）—— 那是计划文档的「验证记录」节
- ❌ **门禁日志** → 落 `<缓存目录>/门禁与走查日志/`
- ❌ **可修改的中间产物** → 那是缓存

## 四、命名与引用

- 文件名**带轮次/日期**，便于按轮检索。
- 计划文档按**裸文件名**引用证据（不写完整路径），故**写就之后不改名**。

## 五、与「完成宣告」的挂钩

完成宣告里凡涉及人工验证的条目，**引用本目录的一份证据**才算数。
**「我验过了」不是证据。**
```

## 什么时候生成本容器

| 情况 | 建议 |
|---|---|
| **有**任何需要人看才能判断正确性的东西（UI、渲染、视觉、交互、音频） | **生成** |
| 纯后端 / 纯库 / 纯 CLI，验证完全靠自动化断言 | **可以不生成** —— 门禁退出码就是证据 |
| 有需要给外部（审计、客户、上游）展示的验收材料 | **生成** |

> **触发信号**：**第一次出现「这个我肉眼看过，没问题」这句话。**
> 那一刻起就需要本容器 —— 否则那句话在下一轮**无法被复查**。
